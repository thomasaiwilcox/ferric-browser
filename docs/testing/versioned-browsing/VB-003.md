## Probe and observed behavior

`tst_versioning_lifecycle_probe.qml` uses real `WebEngineView` instances under a fresh off-the-record `WebEngineProfilePrototype` and a synthetic `data:` document. Its page has a mutable in-memory object, a dirty textarea, `freeze`/`resume` handlers and a background timer. The view moves visually from a disposable source `ApplicationWindow` to a separate retention window. The source window is then destroyed. The retained view is resumed and still has the original object identity and unsaved textarea value; both lifecycle handlers mutated the object, and the timer continued after resume. A new view of the same document does not have that object. This demonstrates retained instance continuity for the tested path, not a clone or a historical snapshot.

VB-031 corrected a fixture initialization-order weakness: the prototype's `instance()` had been evaluated in a property initializer before the instance existed, leaving the old test view with a null profile binding. The fixture now obtains the instance in `initTestCase`, rejects a null instance, and asserts each view uses that exact profile object. The corrected probe passed again offscreen and on Wayland; the earlier runs alone did not prove the off-record profile claim.

The first probe intentionally created the view under the source window and moved only its visual parent before destroying that window. It failed: `lifecycleState` became undefined after source destruction. A JavaScript reference and visual reparenting therefore cannot be treated as an ownership lease. The passing strategy constructs the view under a long-lived retention owner before showing it in the source; it moves the visual parent back before source destruction. Production code must retain that owner and the exact profile instance until all views/callbacks are released. This does not authorise cross-profile reparenting.

The visible-view test requested `Frozen` while Qt recommended `Active`. Qt warned that the transition was refused, and the observed lifecycle stayed `Active`. The retained-view test hides the view, observes a `Frozen` recommendation, then observes actual `Frozen` and `Active` transitions before reporting success. Qt's [public WebEngineView lifecycle contract](https://doc.qt.io/qt-6/qml-qtwebengine-webengineview.html) describes the visible-page restriction and says `Discarded` to `Active` reloads; the probe never uses discard as preservation. The public QML API has no view-clone operation, and the new-view check establishes that loading the same document did not carry the sentinel.

## Capability and privacy decision

The `versioning.live_retention` **primitive gate** is supported only for a retention-owned, same-profile view on this Qt/Wayland fingerprint. `production_enabled` remains `false`: there is no stash command, reducer lease, renderer-loss response or shutdown confirmation yet. A failed future fingerprint or lifetime qualification must leave user-facing LIVE unavailable. Frozen retains a mutable page, not a fixed timestamp.

No normal profile, production account, network service, cookie or credential was used. The fixture has only synthetic local content and an off-the-record engine profile.
