# VB-042 — Add explicit sensitive capture consent and page policies

Status: verified for explicit one-use page-capture consent and policy enforcement; production page capture remains gated by other slices.  
Baseline SHA: pack baseline `deea458d92bcf6d8fbea7b04af17823b5882cc1b`  
Implementation SHA or uncommitted-tree description: shared uncommitted worktree; changes are not committed  
Affected requirement and invariant IDs: VERSION-003, VERSION-009; VB-I04, VB-I12, VB-I14, VB-I15

## Behavior or investigation

- Added profile/global `versioning.page_capture` and `versioning.editable_capture` settings with typed `ask`/`deny` values. `ask` is explicitly documented as permission to ask, not standing consent.
- Sensitive archive requests now remain unavailable unless issued by the current keyboard/UI request path and owned by a normal durable profile. A `deny` policy returns a payload-free `sensitive-capture-denied` reason; editable capture has its own policy gate.
- Added an application one-use consent preparation/confirmation API. Its fixed-copy preview carries only a bounded page count; the returned authorization is bound to the exact captured scope, native owner, configuration epoch, and runtime revision. Cancellation invalidates its preview.
- The versioning panel and user configuration docs state that archives may contain personal data, secrets, and resource URLs and are not sanitized. The panel does not call them secret-free.
- The disclosure distinguishes ordinary local-file protection from encryption: archive files are expected to use restrictive local permissions, but same-account access and backups remain in scope.
- Private/ephemeral persistence is not made configurable. Existing structural capture construction requests structural-only data; automatic checkpoints do not invoke page capture.
- Connected the application consent protocol to the Rust-held native QML dialog. QML receives only the exact operation ID and fixed disclosure copy; it cannot create a preview, selector, or approval permit. Acceptance consumes the preview once and schedules reservation/staging; decline and stale active-target changes cancel that exact operation.
- Editable values and selection-position metadata have independent default-off UI opt-ins. Rust binds both booleans into the one-use authorization and chooses matching fixed disclosure text; selected text itself is explicitly not captured by the selection option.
- A consent refusal after structural preparation retains the exact runtime effects produced by identity binding and routes them through the normal Qt effect/checkpoint bridge, instead of silently dropping the state-change notification.
- The versioning panel's archive action remains disabled behind the VB-057 release gate. The command route remains fail-closed, so the new native path is not exposed as a production feature.

## Consent callback correction — 2026-09-29

The production consent loader now lives in `FerricVersioningConsentHost.qml`,
which owns the dialog instance identifier used by its decision handlers. The
previous handlers in the chrome referred to `dialog.pageCaptureMode`, but that
identifier belonged to the dialog's separate QML component and was unavailable
in the handler's scope. This prevented page acceptance/cancellation and stash
cancellation from reaching their application callbacks.

The new `tst_versioning_consent_host.qml` exercises the production host and
dialog through their action methods. Its offscreen Qt 6.11.2 run passed 7/7
checks (including setup/cleanup), covering exact operation routing, dialog
release after acceptance, cancellation, a refused native decision, incomplete
disclosure and continued refusal of stash approval. A disposable copy with the
old `dialog` references restored failed four cases with `ReferenceError: dialog
is not defined`; the corrected production source passes without QML warnings.
This qualifies the QML callback wiring, not the still-disabled archive release
or a full native application capture journey.

On the current source, a refused acceptance no longer leaves the obsolete
dialog visible until an unrelated work tick. The Rust method can consume or
cancel that preview even when it returns `false`; the QML host now retires only
the matching displayed operation and schedules an immediate Rust refresh after
every exact page decision. A stale dialog signal for an operation already
replaced in the window is ignored. The new regression first failed both
cases, then passed with the fix; the focused Qt suite passed 9/9, including
refused decline. The broader offscreen QML suite passed 173 checks with six
environment-gated skips on the same source. The refresh
may show the same preview again if Rust still owns it, so QML does not treat
its local dismissal as authorization or proof of cancellation. This remains
QML callback evidence, not an integrated native capture.

Command: `QT_QPA_PLATFORM=offscreen QT_QPA_PLATFORMTHEME=
QT_QUICK_BACKEND=software /usr/lib/qt6/bin/qmltestrunner -input
crates/ferric-browser-engine-qt/tests/qml/tst_versioning_consent_host.qml`.

## Privacy and ownership review

- The route resolves the active normal durable owner before considering page policy; private/ephemeral owners are rejected before persistence.
- `ask` does not authorize data collection. Page capture remains unavailable to users until native release qualification and VB-057 enablement; implementation wiring alone is not a release claim.
- No claim is made that safe metadata or a redacted sidecar sanitizes an archive.
