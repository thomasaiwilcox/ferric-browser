## Native qualification

The public Quick-profile probe now uses its real `WebEngineView` and a disposable HTTP server bound to 127.0.0.1. After two `setCookie` calls with empty domains and explicit `http://localhost:<port>` and `http://sub.localhost:<port>` origins, the server observed each synthetic host-only cookie on its own host and its absence on the other host. The subdomain control proves that cookie delivery works on the second host; the negative result is not merely a failed request or blanket cookie rejection. The server keeps only presence booleans, never the request's Cookie header. This verifies that conversion recipe's host-only *write* scope for a fresh off-record profile on this Qt build; it does not recover host-only provenance from an arbitrary source callback. A non-dot domain passed directly to `setCookie` would be broadened by Qt's documented rule and is not used for host-only conversion.

The callback retained raw synthetic name/value bytes, origin-host versus domain strings, distinct paths under one name, a session marker and a persistent expiration, plus Secure and HttpOnly flags. The native input objects carried SameSite Strict, Lax and None; all three came back as `Default` in the installed Qt 6.11.2 callback (`0` for Lax and None in the probe's enum output; Strict is asserted as `Default`). Thus none of those non-default policies is qualified for exact read-back. The installed public `QNetworkCookie` header exposes no partition-key or source-attribute accessor. Synthetic `Partitioned` and plain headers with the same name/path have the same public identifier, and the parsed `Partitioned` attribute disappears from `toRawForm`. This is representation/collision evidence, not proof that a real Chromium partitioned jar was enumerated. The probe keeps notifications as separate observations, and the application mirror's collision test invalidates conflicting records instead of overwriting under that public key.

The supported descriptor scope evidenced here is only a synthetic fresh-profile subset: opaque bytes, domain/path observation, session/expiry, Secure/HttpOnly and host-only *write* isolation. Generic source host-only provenance, partition identity, SameSite fidelity, source scheme/site attributes, complete enumeration and atomic read-back are unqualified. A quiet rescan is not completion. Full-profile strict identity/snapshot/seed/apply gates and all production capability flags remain false. No narrower positive strict-cookie backend certificate is issued.

The matrix reported SameSite callback policy `Lax=0, None=0`, matching `Default`; the Strict-to-Default check also passed. Public partition identifier collision and unknown-completeness assertions passed.
- `cargo xtask check --locked --offline` — passed on the final source, including 57 offscreen QML passes, native cookie/Quick adapter/HTTPS probes and workspace tests.
- `cargo clippy --workspace --all-targets --locked --offline -- -D warnings`, `git diff --check`, pack validation and checksum verification — passed.

The proposed `tests/qml/tst_versioning_cookie_identity.qml` was not added as a standalone QML test: the public `QWebEngineCookieStore`/`QNetworkCookie` conversion surface is C++, and QML JavaScript cannot inspect HttpOnly or partition identity. The existing QML Quick-view fixture plus its native C++ probe provide direct browser requests and typed callback inspection without a mock or a skipped QML-only assertion. This is an evidence-location substitution, not a claim of broader capability.

## Privacy and ownership

Only fixed synthetic cookies in a fresh off-the-record profile and a 127.0.0.1-only disposable server were used. No normal profile, external account, Chromium database, private API or debugging endpoint was touched. The server stores a boolean for the synthetic marker and never logs Cookie headers, names or values. `QNetworkCookie` values remain in native probe memory; no production cookie persistence or UI projection was added.
