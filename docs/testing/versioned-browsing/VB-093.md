## Behavior or investigation

Added [engine-compatibility.md](engine-compatibility.md), separating native
capability-certificate validity from stored-data readability. It defines the
runtime fingerprint fields, component-scoped invalidation triggers,
requalification sequence, explicit old/new schema handling, unsupported
archive-backend refusal, and safe capability disablement without deleting
commits or silently weakening fidelity.

The core capability requirement now has an exact-fingerprint check: a
certificate for another Qt/WebEngine/Chromium/package tuple resolves as
unqualified, including a negative/unsupported finding. Negative evidence is
runtime-scoped and cannot be carried over to a changed runtime as if it were a
current result. Archive object references carry a bounded backend identifier;
new captures label the current public save representation
`qt-webengine-mhtml-v1`. The archive-view route accepts only this exact ID.
Unknown or absent IDs remain readable metadata but cannot trigger materialized
viewing, so old objects are retained rather than guessed or replaced by live
navigation.

The policy uses the current manifest behavior as its conservative baseline:
writers now emit schema 3, schemas 1 and 2 have explicit in-memory migrations,
and unknown older/newer schemas fail closed. The migrations do not modify
stored bytes. Schema 1 ignores any smuggled archive-backend claim; schema 2
ignores any smuggled partial-page policy or page-local archive failure claim.
Legacy archive references remain listed but unopenable without a qualified
backend.
The later VB-050 provenance check separates readability from new publication:
older stored manifests missing archive/sidecar intervals can still decode,
while current supported archive or sidecar objects cannot be newly encoded
without their interval evidence. A regression first showed the missing-field
write was accepted, then passed after validation tightened; schema-1 migration
and unknown-backend tests remain in the storage versioning suite (72/72).
This preserves stored bytes without silently fabricating capture timing.
Unknown engine fingerprints may leave structurally valid bytes readable, but
they cannot authorize a runtime-dependent action.

## Mandatory active-runtime capability check — authored 2026-10-06; not run

Source review found that `CapabilityRequirement::check` could report a
supported or unsupported result without receiving the active runtime
fingerprint. Although the fingerprint-aware method was already available, the
unchecked method left a public route for callers to reuse stale positive or
negative evidence after an engine upgrade. Removed that evaluator so the
requirement API now requires the exact active fingerprint for every result;
the existing focused capability tests were adapted to supply it explicitly.
These source and test changes are authored but unbuilt/unrun under the
end-of-goal verification deferral. This narrows the stale-certificate hazard
but does not supply a second-runtime matrix or unblock VB-090 integration.

A follow-up inspection found that the bounded fingerprint type also accepted
literal `unknown`/`unavailable` placeholders. The constructor now rejects
unknown-sentinel components (case-insensitively), and the focused regression
iterates the sentinel set. That test is likewise authored but unbuilt/unrun;
no runtime qualification is implied.

The exact-tuple regression now independently changes Qt, Qt WebEngine,
Chromium base, security patch, and package revision and requires each variation
to resolve as unqualified. It is authored but remains unbuilt/unrun under the
same deferred verification campaign.
