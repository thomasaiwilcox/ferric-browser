# VB-028 — Normal-profile context scope

Status: in progress; context aggregation regressions passed the application/workspace campaign. A disposable native single-window flow now succeeds, but multi-window aggregation is not qualified.
Baseline SHA: `deea458d92bcf6d8fbea7b04af17823b5882cc1b`
Implementation SHA: uncommitted working tree.
Affected requirements and invariants: VERSION-001; VB-I04, VB-I09, VB-I14, VB-I18.

## Behavior implemented

Context capture resolves the persisted context registry from the source window's current normal-profile/native owner, then admits only the exact still-live windows and tabs whose profile, context membership, order, and identities match the saved membership. The source member must remain valid. Closed windows, changed membership, duplicate identities, transient/private state, stale context ownership, and cross-profile members fail or are recorded as bounded invalid-member reasons rather than widening capture scope.

Each admitted window is projected through the existing structural window path. The manifest records bounded per-window capture intervals and member ordinals, not a claim of an atomic simultaneous snapshot. Runtime window/tab identifiers, context labels/workspace data, and compositor/layout geometry are not serialized. Structural context capture remains distinct from cookie or page-content capture.

Identity allocation, per-window projection, and complete manifest validation now precede all `BindStructuralIdentity` reducer events. Generated logical IDs are checked against existing and already planned IDs across the whole context. The manifest revision is precomputed from the exact number of admitted member events; a failed projection cannot leave only some context members bound.

## 2026-10-02 disposable native continuation

A fresh offscreen normal-profile process accepted `context-create work --profile default` and `context-enter work`, but initially rejected `context-save work`. The exact IPC diagnostic was `no live windows belong to this context`: the Qt command handler compared the core profile's display label (`Default`) to the context's stable profile name (`default`). The save and same-context-window selection paths now compare the exact current profile name and core `ProfileId` instead of a label. With this correction, a second fresh disposable profile accepted context creation, entry, and membership save. An exact context-scoped structural commit was written to its profile-local `vb_commits` table; its decoded manifest had `scope=context`, one member, ordinal 0, a bounded capture interval, and no compositor layout. No personal profile was read.

The two-window extension exposed a separate boundary. A normal `window-new --profile default` creates another `BrowserUi` with its own `IdSource`, so both live windows initially allocated `windowid-2`. Its QML registry also captured the secondary ID before profile bootstrap and reported an empty ID. The Qt bootstrap now uses a process-shared monotonic ID source, while isolated runtime tests retain deterministic local IDs. The QML registry refreshes the secondary identity after bootstrap and refuses to publish a collision. Focused core/runtime tests passed. A fresh disposable native process then reported two distinct live owner IDs, `windowid-6` and `windowid-16`.

This did **not** finish aggregation. At that point the primary application runtime's `windows` projection contained only its own window; a CLI command explicitly addressed to the second live ID was rejected by the primary IPC request owner. Consequently the synthetic two-window application test did not prove real cross-window capture. The routing gap was addressed in the continuation below; the cross-window capture coordinator remains outstanding. Do not infer aggregation from a shared registry or a successful one-window commit.

After the process-shared ID change, `cargo test -p ferric-browser-engine-qt --locked --offline --lib context -- --nocapture` passed 20 focused tests. `cargo xtask test adapter` passed both default-cache and uncached offscreen startup variants. Strict core/runtime Clippy passed. The native one-window journey is evidence for that narrower path only; the focused Rust tests do not exercise a real second-window capture.

A final fresh-profile run against the rebuilt binary accepted `context-create`, `context-enter`, `context-save`, and a correctly quoted CLI `command -- "commit 'Proper quoted checkpoint' --scope=context"`; the profile-local `vb_commits` table contained the durable commit. Passing the message as separate shell words to `command --` lost its inner quoting and was rejected; that is not evidence of context-capture failure.

## 2026-10-02 exact secondary-owner IPC continuation

The authenticated instance owner now hands an explicitly addressed, typed
`command.execute` or `action.execute` request to a bounded same-process
mailbox keyed by the target window ID and current native owner token. QML
transports only the target identity; it invokes the exact still-live secondary
`BrowserUi` and rejects a missing, ambiguous, or changed owner. The secondary
executes the request against its own application state and returns the IPC
response. Focused Rust tests cover typed explicit-window selection and
stale-token refusal.

A fresh disposable offscreen normal-profile process had primary
`windowid-6`/`profileid-5` and secondary `windowid-16`/`profileid-15`. A
direct framed IPC `tab-open` addressed to `windowid-16` returned a new
`tabid-25` and a command context naming `windowid-16`/`profileid-15`; an
addressed `browser.tab.open` action returned `tabid-29` from the same owner.
Addressed `context-create`, `context-enter`, and `context-save` also succeeded
on the secondary. A request for absent `windowid-99999` was rejected. This
proves secondary-owner command delivery, not a two-window context commit.
After another tab opened, an addressed context commit refused `stale-owner`
until membership was saved again. The next addressed commit returned pending,
and the disposable profile's `vb_commits` row was durably present with
`scope=context` and exactly one manifest window. This verifies the secondary
owner's one-window publication and the membership guard; it is not evidence
that the primary and secondary were aggregated.

The primary and secondary still hold separate application projections.
`context-save` sees only its local window, and the primary context-capture
preparer cannot project the secondary from its runtime. Owner-level
`windows.query` and operation tracking are likewise not federated. The next
continuation must coordinate exact per-window snapshots and bindings across
both live owners before one context manifest is published. VB-028 remains in
progress.
Strict Qt Clippy, workspace formatting, and the complete `cargo xtask check
--locked --offline` pass after the routing change.

## 2026-10-02 separate-application capture core

The application boundary now has a bounded federated context preparation and
durable-begin path accepting separate mutable `BrowserApplication` owners. It
resolves membership from the source's current saved registry, verifies an
unambiguous exact runtime window in each owner, compares durable profile UUIDs
and live context/tab order, projects each owner's existing structural scope,
and validates the full aggregate before emitting identity-binding reducer
events at their respective owners. Peer effects are returned with their exact
window ID for adapter checkpointing. The source submits one structural publish
to its profile storage worker; this is still only pending until the durable
commit event.

Focused tests created two independently bootstrapped process-unique application
owners for one disposable profile. Both windows were included with separate
member ordinals and intervals, and the resulting two-window context manifest
was read back from the durable commit row. A different-profile peer was
reported as an invalid member without binding its identity. The 31 focused
application capture tests, all 156 application tests, and strict application
Clippy passed. This is
application-level evidence, **not** a native Qt two-window witness: the Qt
adapter still needs an exact synchronous owner handoff, federated
`context-save`, and delivery of each peer's reducer effects. VB-028 remains
in progress.

The next core seam is now present as an owner-issued, non-serializable
`ContextWindowCaptureCandidate`. Each application owner projects only its
own exact window into this Rust-held object. The source can assemble a
context manifest from candidates only after comparing them with its current
saved context ID, member ordinals, runtime tab order, normal-profile UUID,
and logical-ID uniqueness; it does not bind identity or write storage in
that step. Binding a candidate at its originating owner rechecks the exact
native profile instance, reducer revision, context, and tab order. The
two-owner test exercised candidate assembly, a missing-peer invalid-member
record, and refusal after the peer opened another tab. The 156 application
tests and strict application Clippy still pass. A bounded process-local Qt
handoff and a native two-window witness remain to be implemented; the
candidate API alone does not enable cross-window commits.

## 2026-10-02 bounded Qt owner-handle seam

The Qt adapter now stages one owner-issued candidate in a bounded,
process-local Rust mailbox under a random opaque handle, typed window ID,
and exact `BrowserUi` owner token. QML can request only the current saved
context UUID and a handle; it never receives the structural page projection
or reducer binding plan. The originating live `BrowserUi` alone can consume
that handle, then applies any binding effects through the existing
revision-aware checkpoint bridge. A mismatched owner or stale token cannot
consume it; entries expire and the mailbox refuses over 256 staged captures.

`cargo check -p ferric-browser-engine-qt --locked --offline -q` passed after
the new qinvokables were compiled. The two focused mailbox tests passed and
the full application suite passed 157/157, including a new check that an
unsaved or former native context owner cannot expose a capture reference.
Strict Qt Clippy passed; the build emitted only pre-existing Qt/C++ header
warnings outside the Rust `-D warnings` gate.
This is still a handoff primitive, not an integrated context command: no QML
coordinator yet gathers the handles for `context-save` or a context commit,
and no native two-window aggregate has been published. VB-028 remains in
progress.

The source owner now retains an immutable aggregate plan and exact saved
context record before any binding. The process-local mailbox provides
bounded, unique snapshots of staged captures and one-use receipts only after
the originating `BrowserUi` accepts the binding through its revision-aware
effect path. Publication requires all expected window/owner-token receipts,
the unchanged saved context, and the source reducer's expected revision. An
application regression reached a durable two-window aggregate through this
prepared-plan path. The aggregate interval now begins at the earliest actual
owner-capture interval, fixing an intermittent refusal when source assembly
happened later. The full application suite passed 157/157; its focused
two-owner regression passed ten consecutive repetitions. Three focused Qt
mailbox tests passed, including partial-receipt refusal.

Interactive structural `commit --scope=context` now queues a UI coordinator
instead of immediately publishing the source's local-only snapshot. The
coordinator obtains the source's saved member order from Rust, preflights
exact live window IDs, owner tokens, profile and normal-profile status,
stages one Rust-held candidate at each owner, asks the source to prepare the
aggregate, binds each candidate at its originating owner, and finishes only
after Rust verifies every receipt. QML handles contain no structural payload.
The new coordinator QML test passed exact two-owner ordering and refusals for
ambiguous/stale owners and a failed peer binding. Qt `cargo check` and strict
Qt Clippy passed after this wiring. This does **not** yet qualify VB-028:
`context-save` still persists only local members, the federated route has no
native two-window durable witness, and addressed IPC context commits do not
yet use this coordinator. The coordinator is a live command path only for
already-saved complete membership. VB-028 remains in progress.

## 2026-10-02 native cross-owner save and commit

`context-save` now queues an exact-owner handoff rather than serialising the
source window alone. Each live normal-profile context window stages a
Rust-held `ContextMember` under an opaque expiring handle, then rechecks its
profile UUID, native instance, reducer revision, context, tab order and safe
descriptors before issuing a one-use confirmation. The source validates
unique same-profile candidates, its own context record and reducer revision,
and all owner confirmations before replacing saved membership. QML sees only
window identities and handles; it never receives tab URLs, titles, or the
structural capture. The interactive and addressed IPC structural context
commit routes now use the same coordinated capture path. IPC reports
acceptance while that UI work is pending; durable publication must still be
established from the storage outcome, not that immediate response.

A fresh offscreen browser using only `/tmp/ferric-vb028-native-mSbYL8` created
the `work` context and two distinct same-profile windows (`windowid-6` and
`windowid-16`). After both entered the context, `context-save work` wrote a
profile-local `contexts.json` record with both window IDs and their exact tab
IDs. An addressed IPC `commit 'Two owner checkpoint' --scope=context` then
produced a durable `vb_commits` row: `scope=context`, two manifest windows,
`context_member_count=2`, ordinals 0 and 1, and bounded per-window capture
intervals. The stored manifest contained neither runtime `windowid-` strings
nor a layout field. After both windows gained tabs, a commit against stale
saved membership produced no row. Re-saving membership recorded two tabs for
the first owner and three for the second; a new durable two-window commit
contained corresponding page counts 2 and 3. The disposable browser process
was stopped; its test data was retained for inspection. No personal profile
was accessed.

The full application suite passed 157/157. The focused Qt context suite
passed 23/23; the QML coordinator suite passed all seven cases, including
ambiguous or stale owners and failed peer confirmation/binding. Qt `cargo
check -p ferric-browser-engine-qt --locked --offline -q`, formatting, and
`git diff --check`, strict Qt Clippy, and the complete `cargo xtask check
--locked --offline` repository gate passed. A closed saved peer fails closed in
the live coordinator; the application-level missing-peer manifest test records
it as an invalid member without claiming an atomic cross-window instant.
VB-028 is verified for structural normal-profile context capture. This does
not qualify cookie capture, live retention, or the later release milestone.

## Remaining limits

Membership is checked synchronously from Ferric's current registry/runtime projection; it is not a compositor snapshot or cross-window transaction. Members that change or close after capture preparation are not retroactively claimed as one common instant.
