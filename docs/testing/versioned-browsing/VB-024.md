## Native profile construction constraint

Pinned Qt 6.11.2 source confirms that `WebEngineProfilePrototype::instance()`
returns null if another profile already uses its persistent storage path. The
earlier primary-surface restore child constructed a prototype for the
same source profile path; this is not a valid independent profile allocation.
See [`componentComplete` and `instance`](https://github.com/qt/qtwebengine/blob/a33fa2a897e5ee58e385b3f88dc247d99fca56db/src/webenginequick/api/qquickwebengineprofileprototype.cpp#L279).
The fixed startup-failure path closes only that child and reports the failure
to its captured source UI, rather than quitting the process or leaving a false
success indication.

The native new-window route requires a tab-capable **same-profile
window adapter**, not another profile at the same disk path. Reusing the exact
source profile must also reuse its interceptor without replacing it, avoid
duplicate profile signal handlers, and join the instance's discovery/shutdown
lifecycle. Requests with retained exact identities can still route to their
known window; a new callback whose QML view origin is unavailable is managed by
the one adapter that owns the emitting profile, without claiming tab identity.
No pointer-sharing shortcut, private engine API, or new directory masquerading
as the original profile was introduced. The implementation below addresses
construction and signal ownership; remaining integration qualification is
independent of the strict stash/cookie API gaps.

Native retest with a new disposable normal profile confirmed that failure is
now reported to the source as “Restore window profile could not initialize;
current work is intact.” The source's registry entry, owner token, window/tab
IDs and sequence were unchanged, and subsequent IPC queries succeeded. This
qualifies the observed failure path only; it is not a successful live restore.

## Nested restore ownership continuation

The existing 32-window limit applied separately to each restore host, so a
restore descendant could create another 32-window tree even while the entry
window's discovery and shutdown projections were bounded. The owner now carries
the exact parent-owner link into each tab-capable restore surface, counts retained
windows across that ownership tree, and refuses allocation once the entry
window's 32-descendant budget is full. A missing, misbound or cyclic owner link
fails closed. A hidden, shutdown-approved parent remains retained until its
owned descendants have closed; a descendant discovery change rechecks that
deferred release. This keeps nested windows within the same bounded discovery,
download-routing and shutdown ownership scope instead of allowing unbounded
depth or destroying a live descendant's only owner. While such a parent waits
for descendants, discovery still traverses through it, and shutdown/cancel
requests reach those descendants rather than treating the approved parent as
the end of the ownership tree. The entry window's shutdown participant count
now uses the retained tree rather than counting only direct children. Its
separate live-window registry pass excludes hosts already owned by that tree,
so a restore descendant is not asked to close or cancel twice merely because
it also appears in discovery.

QML regressions for global nested capacity, deferred parent release,
descendant discovery/shutdown, exact host ownership, nested download routing
without ID-only fallback, and misbound/cyclic owners are authored in
`tst_versioning_window_owner.qml`.
They passed in the 2026-10-02 full QML check.
Native active-download/dirty-page shutdown, multi-page safe-GET/sidecar journeys,
and profile-wide download callback delivery remain unqualified. Current-window
replacement remains gated by the missing live-retention capability.
