## Behavior implemented

The profile-local versioning journal stores fixed redacted summaries, caps retained events, and prunes old terminal-operation references. Commit deletion begins with a counts-only preview whose opaque confirmation snapshot binds profile, commit, pin/reference state, active-operation state, and object graph. Confirmation revalidates the snapshot in an immediate SQLite transaction. A pinned commit, child commit, named reference, or active operation blocks deletion.

Deletion-preview cancellation now requires the originating window, and a
confirmation attempt from a different window leaves the rightful owner's
preview intact. The owner-bound regression passed in the 2026-10-02 workspace
Rust suite.

Object collection defers while any capture reservation is active. At quiescence it computes roots from profile-local commit links, verifies referenced objects, marks missing/corrupt objects unavailable, and moves corrupt/unpublished/unreferenced files into private profile quarantine. Recovery does not unlink arbitrary external paths or claim forensic erasure. The profile byte budget rejects additional captures rather than evicting explicitly pinned history.

The production capture reservation now accounts for durable commits plus
active staging captures against the GC's 100,000-row ceiling, reserving one
future commit slot per admitted capture. Publication separately checks durable
rows as a backstop for pre-existing staging operations. An authored regression
uses exactly this ceiling in a real `ProfileStore`: the final slot can be
reserved and published despite another profile having its own active capture,
a concurrent second reservation refuses without writing another operation or
journal event, and a simulated pre-existing operation cannot publish beyond
the ceiling. It has not been run under the user's verification deferral; the
commit-row cap is not evidence for SQLite/WAL physical growth or same-UID
filesystem races.

The orphan-object sweep now rejects an object whose inode has more than one
hard link, matching the existing corrupt-reference quarantine rule. Otherwise
moving the profile link into quarantine would preserve a shared inode still
reachable through a path outside the profile. The new synthetic regression
creates that outside link, expects `UnsafeEntry`, and checks that both links
remain unchanged. It passed in the focused storage suite; no broader

## Privacy and remaining limits

Journal summaries are fixed code-owned phrases and never include page text, cookie data, credentials, paths, or URLs. Quarantine preserves recoverability and may retain disk usage; it is not secure deletion. Overall quota accounting and crash/fault qualification remain part of the final storage campaign and VB-091.

## SQLite WAL retained-size control — verified in 2026-10-05 campaign

Each normal profile connection now explicitly configures SQLite's automatic
WAL checkpoint threshold to 1,000 frames and a 16 MiB `journal_size_limit`.
Automatic checkpoints are SQLite `PASSIVE` checkpoints; they copy eligible
frames but do not truncate the WAL. A large committed transaction can therefore
leave the physical WAL above the retained-size target until an explicit reset.
An orderly profile flush requests a `TRUNCATE` checkpoint and reports a busy
result as a flush failure. Authored storage regressions check both connection
settings, commit a bounded 20 MiB write that crosses the automatic checkpoint
threshold, explicitly flush and require the WAL to fit the configured limit,
verify that flush leaves the WAL at zero bytes, and reopen the profile to check
committed data survives.

The final storage suite and full current-tree gate passed these regressions,
including explicit flush and pinned-reader failure. This bounds retained WAL
size after an explicit reset/checkpoint and truncates it at successful orderly
flush; it is not a hard limit on WAL growth during a transaction or before an
explicit truncate, while another connection prevents checkpoint completion,
or an exact profile-volume quota. See SQLite's
[journal-size-limit](https://sqlite.org/pragma.html#pragma_journal_size_limit)
and [WAL checkpoint](https://sqlite.org/pragma.html#pragma_wal_checkpoint)
semantics. VB-026 remains in progress and VB-091's physical/fault campaign
remains open.
