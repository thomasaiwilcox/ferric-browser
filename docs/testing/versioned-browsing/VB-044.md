## Behavior or investigation

- QML starts `WebEngineView.save` only after Rust has accepted the exact one-use consent and the file-only worker has returned a private staging target for the exact captured normal-profile tab.
- Rust returns the staging path only for a one-use operation/tab claim. Since Qt Quick's public page-origin getter is unsafe for some callbacks, the same-profile owner tree permits only one capture at a time and correlates the profile-wide event using the private exact directory/name, SavePage/MHTML facts, bounded numeric ID, and active Rust operation claim. Completion still requires the captured view to be live with the same document target and runtime revision.
- The public save request is auto-started; it is not globally accepted and never enters the ordinary download picker. Ordinary non-save downloads retain their existing path. Any duplicate, mismatched, or otherwise ambiguous page-save request during the profile capture slot cancels both the new request and any original in-flight save, quarantines the exact stage path and both IDs before calling Qt cancellation, and then cancels the operation. An ambiguous owner that matches the exact stage path follows the same fail-closed path.
- A stale or expired Rust operation cancels an in-flight QML download and retires its ID before dropping the route. The native timer also cancels and cleans up after its bounded wait.
- Retired page-save IDs and exact temporary paths are kept in fixed 512-entry callback quarantines. A new page capture is refused before it can create another download if there is not room for its own and one duplicate late callback. Retired-path tombstones remain for the process lifetime because late native callbacks have no public terminal guarantee; neither cache evicts an unresolved identity or grows without bound.
- An interrupted, cancelled, timed-out, superseded or otherwise abandoned native save also quarantines that logical tab from further page-save requests for the lifetime of its owning window. This avoids reusing a Qt view after the observed auto-start cancellation/late-completion ordering while preserving ordinary browsing and non-page downloads; a replacement view with a new tab identity remains eligible.
- The archive button remains disabled pending VB-057. The supported VB-004 primitive is only the narrowly observed public single-view/exact-path MHTML route, not production enablement.

## Outstanding ordinary-download overlap and refusal ordering — 2026-10-02

The disposable native probe now holds a real ordinary Qt download request,
starts a page save through the shared production admission function, then
accepts the ordinary request on the next event-loop turn while the save is
still pending. Both requests complete independently. Immediate Rust-admission
refusal is also tested before this overlap, with exact ID/path retirement and
no refused file at probe end. The default `cargo xtask test archive` passed
this sequence, the remaining archive-isolation checks, and the durable MHTML
adapter follow-on. This is genuine simultaneous outstanding Qt requests,
though it does not establish simultaneous byte transfer or Ferric's normal
download-ledger behavior.
The complete `cargo xtask check --locked --offline` subsequently passed on
this source, including the default native archive/cookie probes, QML checks,
and workspace Rust tests. The opt-in reverse-order failure below remains a
release blocker despite that passing default check.

The reverse order remains unqualified. Run
`FERRIC_ARCHIVE_PROBE_REFUSAL_AFTER_CONCURRENT=1 cargo xtask test archive`
to reproduce it in a disposable Weston profile: the overlapping save and
ordinary download finish, the next page save is refused and its path/ID are
retired, but a subsequent save remains `DownloadInProgress` beyond the native
wait despite writing bytes. Equivalent ordering failed in repeated native
runs; the retained opt-in diagnostic exited 2. Its
later save ID was 5, the last finished ID was 4, and the refused path held
zero bytes. Omitting the refusal made the later save complete. Deferring Qt
`cancel()` one event-loop turn made the later save complete but transiently
created an archive at the refused path, so that experiment was reverted. The
default probe retains immediate fail-closed cancellation; production code and
the release gate were not relaxed. This sequence requires a bounded native
cancel/cleanup design and repeat qualification before VB-044 or VB-057 can be
promoted.

A follow-up instrumented run on the installed Qt 6.11.2 made the callback
ordering precise. Immediately after `cancel()`, the refused request reported
`DownloadCancelled` and `isFinished=true`, with no `downloadFinished` signal.
Waiting for that signal before starting another save timed out. With the
original sequence restored, a later `downloadFinished` for the refused ID
reported `DownloadCompleted` only after the next save had started; that next
save then remained in progress. The refused file remained absent. Calling
`pause()` immediately before `cancel()` reproduced the same failure and was
reverted. Therefore a mere wait for the refused request's finish signal or
pause-before-cancel is not a qualified workaround. The native diagnostic now
records the refused ID, immediate state, and later finish state on failure.
Qt's public [download-request contract](https://doc.qt.io/qt-6/qwebenginedownloadrequest.html)
documents auto-started page saves and cancellation from the first direct
request handler; this observed reverse-order lifecycle still needs a bounded
private-stage cleanup and repeat native qualification.

The public [`WebEngineView.save` documentation](https://doc.qt.io/qt-6/qml-qtwebengine-webengineview.html)
describes that method as a SavePage action plus automatic acceptance of the
next download. A disposable opt-in probe replaced that shortcut with
`triggerWebAction(SavePage)`, set the exact private stage path and MHTML format
in `downloadRequested`, and accepted only the admitted request. The callback
initially saw `DownloadRequested` (state 0); the admitted page save and
ordinary download completed. Nevertheless the reverse-order refusal still
made the later page save hang. A second opt-in run left the refused pending
request unaccepted, relying on Qt's documented default rejection instead of
calling `cancel()`; it also hung the later save, with zero refused-path bytes.
These two variants were reverted from the probe and never enabled in
production. They show that the `save()` shortcut's automatic acceptance and
the explicit `cancel()` call are not, individually, sufficient explanations
for the reverse-order failure on this Qt build.

## Current-runtime reverse-order recheck — 2026-10-03

The opt-in disposable Weston probe was rerun on the current source with
`FERRIC_ARCHIVE_PROBE_REFUSAL_AFTER_CONCURRENT=1 cargo xtask test archive`.

connected request handler. It does not guarantee a prompt `downloadFinished`
callback for the refused request or safe reuse of this view's save pipeline
after the observed ordering. Pre-dispatch Rust admission is already present,
but the exact request still requires post-dispatch correlation and may be
refused if its owner or operation becomes stale. Do not turn this opt-in
failure into a success by deferring cancellation, accepting transient refused
archive bytes, or treating `isFinished` as `DownloadCompleted`. VB-044 and
VB-057 remain unqualified; production archive capture stays disabled.

An additional disposable variant followed Qt's documented recommendation to
delete an unneeded request after `downloadRequested` returned. It deleted
only the exact refused request via deferred QObject deletion, verified the
object was gone, and still observed the next save write 82,058 bytes without
a terminal callback. The refused path remained empty. That variant was
removed after the negative result; the default native probe and production
route retain their previous behavior. Request-object retention alone is not
the cause on this build, and deletion is not a qualified repair.

## Superseded native-save ownership — 2026-10-03

The runtime work loop previously left an old QML page-save capture occupying
the native slot when Rust had already admitted a different replacement
operation. Because `has_native_page_capture_request()` then described the new
operation, the old capture was not retired and the new one could wait for the

supersession helper. The loop now recognizes a different exact pending
operation, retires the old stage path and request ID before cancelling its

operation before starting the replacement. If bounded quarantine cannot
record the old identity, it keeps the old capture and does not start the new
one.

and its QML suite on the production scheduler change (the final extra

deterministic QML ownership evidence, not a live Qt request-replacement
journey or a fix for the separate reverse-order refusal hang. VB-044 and the

## Pending-save callback and target-path check — 2026-10-04

The pinned Qt 6.11.2 source under `target/versioning-engine-spike` shows that
`ChooseSavePath` queues a save callback before delivering the public
`downloadRequested` signal. For an auto-accepted `WebEngineView.save`, the
request is already `DownloadInProgress` when the application sees it. Its
public `cancel()` first asks Qt to cancel an actual download item; if none
exists yet, it marks the request cancelled and answers it. Qt's
`savePathDetermined(false)` then erases the pending save callback without
invoking it. This is a plausible explanation for the observed late/misordered
finish signal, not proof of Chromium's internal state.

A disposable reverse-order probe tested redirecting the refused request to a
nonexistent parent directory while allowing Qt to answer the callback. Qt
ignored the `downloadDirectory` and `downloadFileName` assignments on this
already-auto-started request: the public path still read as the originally
requested stage path, and that original path was created. The probe exited
on its no-output assertion. This variant was removed; production behavior
and the default native journey are unchanged. Redirecting an auto-started
refusal is not a safe workaround for this build.

## Per-tab native-save retry quarantine — 2026-10-04

The repeated-save diagnostic established that a refused/cancelled auto-started
page save can be followed by a delayed `DownloadCompleted` for the refused ID
after another save begins, while that later save remains in progress. Public
Qt controls tested so far did not reset the same view's save pipeline without
creating refused-path output. Ferric now records the logical tab ID in a
bounded, window-local in-memory quarantine whenever an initiated native save
is abandoned before successful completion. A later archive attempt for that
tab is cancelled before another `WebEngineView.save` call. A later page-save
request from the poisoned view is also rejected at the first request handler
and its exact ID is retired before Qt cancellation, preventing its late finish
from entering ordinary-download finalization. The page itself, regular file
downloads and other tabs remain usable. The tab marker is not evicted while
that owner window lives; if its bounded set fills, the existing window-wide
callback-suppression latch applies.

Authored ChromeInteractions regressions verify that a cancelled or
interrupted save poisons only its exact tab, a later page-save request is
cancelled with its exact ID retired, successful completed-save cleanup does
not poison a tab, and other tabs remain eligible. Production startup checks
the marker before invoking Qt. This is a fail-closed workaround, not a
public Qt reset or proof that replacing the view is required on every platform.
The fixture and latest code have not been run under the deferred verification
instruction. The reverse-order native reproducer still needs final repetition
against the integrated runtime; VB-044 and VB-057 remain in progress, and
production archive capture remains disabled.

## Qt Quick page-origin API and exact-permit route — 2026-10-04

The public C++ `QWebEngineDownloadRequest::page()` accessor exists, but the
source-locked Qt 6.11.2 implementation at
`a33fa2a897e5ee58e385b3f88dc247d99fca56db` is client-specific:
`src/core/api/qwebenginedownloadrequest.cpp` returns the held page only for a
Widgets client and returns null for the QML client used by Ferric's Qt Quick
views. The public QML `QQuickWebEngineDownloadRequest::view()` accessor is not
a safe fallback for viewless callbacks: the pinned implementation dereferences
its adapter client without a null check. See the [public download request
API](https://doc.qt.io/qt-6/qwebenginedownloadrequest.html) and the
[Qt Quick profile download signal](https://doc.qt.io/qt-6/qquickwebengineprofile.html).

The implementation now uses the proposal's bounded alternative for an
authorized archive save: the owner tree permits only one active save per
profile, then correlates the profile-wide callback using the exact private,
one-use staging path, SavePage/MHTML facts and Rust's active operation claim.
Path matching refuses empty values, names over 255 characters, or combined
paths over 4096 characters before owner resolution.
Owner resolution finds that path before touching the unsafe QML `view`
getter; any second or mismatched page save during the capture is rejected.
Rust records this as a permit match, not as a claim that Qt exposed a page
pointer. A native regression now checks a real QML MHTML callback against the
path-only production route, and QML fixtures cover a throwing view getter,
profile separation, path ambiguity, profile serialization and fail-closed
mismatches. These authored tests remain unrun under the deferred final
verification instruction.

This does not solve arbitrary viewless ordinary-download routing: outside the
active Ferric archive permit, existing ownership still relies on the QML view
property, whose lifecycle is not a safe public fallback. Keep that route
fail-closed/unqualified and VB-024/VB-044/VB-057 in progress. The release
matrix is still required; production archive capture remains disabled.

## Same-profile stimulus alternatives audit — 2026-10-05

The installed Qt 6.11.2 public `qquickwebengineprofile.h` confirms the API
boundary directly: `QQuickWebEngineProfile` exposes `cookieStore()`, request
interception, download signals and (since Qt 6.10) `extensionManager()`, but no
public `QWebEngineProfile` accessor. The corresponding `QWebEnginePage`
constructor requires a core `QWebEngineProfile*`; constructing a second core
profile from the same storage paths would not prove shared live profile state
and is not an acceptable substitute.

The extension manager is not a qualified replacement stimulus. Qt documents
Manifest V3 loading and explicitly disallows extensions in off-the-record
profiles, but its public contract does not promise the `chrome.downloads` API
or that such an extension request produces the required viewless profile
download callback. We therefore do not enable an extension, use a private Qt
adapter, or claim the ordinary-download-to-ledger journey is proven. A bounded
native extension experiment on an ordinary named profile could establish a
new candidate route, but it would still need to match the production profile
configuration and lifecycle before serving as evidence.

That candidate is now an authored, test-only experiment in
`crates/ferric-browser-engine-qt/tests/native/versioning_viewless_download_probe.cpp`.
It loads an unpacked MV3 extension through the public profile
`extensionManager()`, triggers `chrome.downloads.download()` from the
extension's background service worker, and requires one native profile
request whose public `QWebEngineDownloadRequest::page()` is null. The QML
callback routes it through Ferric's shared `ProfileDownloadRouting` exact
profile-owner helper, retains that request identity through its terminal
callback, and writes only to a disposable test directory. The dedicated
command is `cargo xtask test versioning-viewless-download`.

This has not been built or run under the requested end-of-goal verification
deferral. It is a test harness, not production extension support or a durable
ledger journey. A passing native result would establish a supported candidate
stimulus for the same profile type; a failed/unsupported result leaves the
current blocker intact. Production profiles and extension settings are
unchanged.

## Qt 6.10.3 cross-runtime recheck — 2026-10-06

To check whether this was limited to the installed Qt 6.11.2 build, I
downloaded an isolated official Qt 6.10.3 runtime under `/tmp` and ran the

public manager contract documents that loaded extensions are disabled and
must be explicitly enabled, so there is no documented activation-free path
to this stimulus ([Qt extension-manager API](https://doc.qt.io/qt-6/qwebengineextensionmanager.html)).

## Public profile-level trigger surface audit — 2026-10-06

The official Qt 6.11.2 API references clarify the remaining public-API
boundary: [`QWebEngineDownloadRequest::page()`](https://doc.qt.io/qt-6/qwebenginedownloadrequest.html#page)
returns null when a download was not triggered by content in a page;
[`QWebEngineProfile::downloadRequested`](https://doc.qt.io/qt-6/qwebengineprofile.html#downloadRequested)
is the application notification/decision point, not a request-construction
API; and the documented programmatic
[`QWebEnginePage::download()`](https://doc.qt.io/qt-6.11/qwebenginepage.html#download)
is page-owned (the local probe observed a non-null page on both tested runtime
lines). The QML profile API likewise exposes the profile signal and download
settings but no profile-level download-trigger method.

This narrows candidate work: a supported witness must originate from
non-page browser/content machinery that actually produces `page() == nullptr`
on the exact production profile, or use a separately approved public adapter
with equivalent ownership evidence. It does not prove that all web-content
routes fail, and it does not resolve the extension-activation crash. Do not
manufacture a fake `QWebEngineDownloadRequest` or route through private core
profile access. The production archive gate is unchanged.
