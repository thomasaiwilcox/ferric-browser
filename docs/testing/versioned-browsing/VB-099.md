# VB-099 — pinned production backend extraction

Status: implementation in progress on 2026-10-08; no capability or release
status promoted. The owner approved engineering toward a maintained pinned
backend, but this Linux x86_64 development candidate is not a release bundle.

The separate `tools/versioning-engine-backend/production/` path now pins the
Qt WebEngine 6.11.2 source archive and an isolated three-file Qt Quick patch.
The patch adds only a v1 native view/adapter-generation identity witness, not
cookie, RTC or download assertions. Its adapter generation rotates on profile
replacement, adopted contents and renderer termination. A zero-fuzz forward
dry-run passed against the unmodified pinned Qt git files, and a reverse
dry-run passed against the patched clean archive extraction. The Ferric QML
host captures the witness with its exact view/profile/Rust view ID and refuses
the stale witness before hiding or freezing a held source. The system Qt path
without those invokables retains its existing behavior.

The clean source build configured with WebEngine Core and WebRTC enabled and
reached Ninja edge 2017/4105 before being intentionally interrupted on
2026-10-08 for transfer to another machine. No engine link or installation
completed; the generated partial build remains only in this host's ignored
`target/` tree. On a different machine, rebuild from the pinned source with
`bash tools/versioning-engine-backend/production/build.sh all`. The source/patch
and local Qt runtime hashes are pinned in
`production/source-lock.json` and `production/system-qt-linux-x86_64.sha256`.
Before interruption, the independently extracted-source comparison
passed twice for 269,594 archive members and the three exact patched files;
the second run included the extra-path check and found no disallowed paths.
The Ferric browser rebuilt successfully with the owner bridge, and the new QML
fixtures parse. Neither result is a native runtime certificate before the clean
engine is installed.
With no backend-selection environment, the rebuilt Ferric binary's loader
still resolves both WebEngine Core and Quick from `/usr/lib`, preserving the
public-Qt default. The exact-bundle loader check remains pending installation.
`production/verify-and-run.sh` is prepared to check exact installed library,
process, QML/resource/locale and loader paths and to exercise wrong-engine,
mixed-process/resource, exact owner, renderer-failure and renderer-sandbox
refusals. These are **planned tests**, not passing evidence until the build,
install and each command complete. No `ForProbe` method is in the patch; the
binary absence check is still pending the clean install.

After installation, record the five installed WebEngine library/process hashes
and deterministic QML/resource/locale tree digest in the two currently absent
`production/owner-abi-linux-x86_64*.sha256` manifests, then run the exact-bundle
verifier's `check`, `test-integrity`, `test-owner`, `test-view-host`,
`test-sandbox` and disposable `run` commands. The backend README documents the
generation commands. Each negative test and live process/renderer observation
must be recorded here before VB-099 can become verified. The build script's
system-Qt manifest and generated-configuration hashes are host-tuple locks;
a different Qt installation or toolchain requires a reviewed new tuple, not
a silently relaxed check. VB-100/101/102 remain later separate capabilities.

The local `target/versioning-engine-spike/install` research tuple is pinned by
[`candidate-linux-x86_64.sha256`](../../../tools/versioning-engine-backend/candidate-linux-x86_64.sha256)
and the QML/resource/locale tree digest. `verify-and-run.sh check` passed, and
its 18-second offscreen `--safe-mode` smoke launch used disposable XDG roots.
Live process maps showed WebEngine Core, Quick and the QtWebEngine QML plugin
loaded from that install. Child processes used its process binary, Core library
and resources. The actual renderer reported `NoNewPrivs: 1`, `Seccomp: 2` and
one seccomp filter; an intermediate zygote reported `Seccomp: 0`. These are
host observations, not a complete sandbox review.

The verified candidate's `test-view-host` run passed 18/18 existing exact-view
QML tests. A disposable system-Qt control also passed 18/18. Chromium emitted
three rejected-widget-message diagnostics on the candidate and five of the
same class on the public control; their release significance remains open.
No strict capability or backlog dependency was promoted by these results.

The separate `check-no-probe-api.sh` release-hygiene check intentionally
refused the research install: exported `ferric*ForProbe` symbols remain in its
WebEngine Core library (and Quick also exposes probe methods). This demonstrates
why the currently passing research build cannot simply become a production
artifact. The separate clean-source patch and owner binding described above
must now pass the full build, source-to-binary and negative/mixed-runtime
tests. See [ADR-0016](../../architecture/ADR-0016-versioning-engine-capability-backend.md)
and the [backend handoff](../../../tools/versioning-engine-backend/README.md).

Source-boundary inspection for extraction:

- The canonical-cookie research patch crosses `qwebenginecookiestore`,
  `cookie_monster_delegate_qt`, `qwebenginepage`, `web_contents_adapter`, the
  renderer frame bridge and its Mojo messages. Seed-if-empty additionally
  changes Chromium `CookieMonster`, `CookieManager` and its Mojo interface.
  Production extraction must remove synthetic fixture constructors, fault
  injection, raw debug returns and public `ForProbe` methods while retaining
  only the bounded, owner-validated operations that have acceptance tests.
- The RTC research path spans `web_contents_adapter`, the media capture
  dispatcher/delegate, renderer-side peer tracker and Mojo bridge. The exact
  Qt Quick owner overlay touches `qquickwebengineview_p.h`, its private state
  and `qquickwebengineview.cpp`; its current QML-invokable lease methods are
  probe-only. Child-capture and frame-activation overlays are diagnostic and
  include failed/unqualified cases; they cannot be carried forward as a
  blanket absence assertion.
- No ordinary viewless-download production patch exists yet. VB-102 must
  design and qualify that origin separately; an RTC or cookie build does not
  satisfy it.

This map is a source review entry point, not a claim that the overlays compose
into a shippable patch. The current minimal patch deliberately excludes those
strict capabilities; build and native qualification remain outstanding.
