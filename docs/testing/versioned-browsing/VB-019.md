# VB-019 — Versioning index migration through the profile store

Status: verified (schema migration and owner boundary only; no capture publication)
Baseline SHA: `deea458d92bcf6d8fbea7b04af17823b5882cc1b`
Implementation SHA: uncommitted working tree atop the baseline
Affected requirements: `VERSION-001`, `VERSION-009`; invariants `VB-I01`, `VB-I04`, `VB-I09`, `VB-I12`

## Behavior

The existing profile SQLite store advances from schema 3 to schema 4. A fresh store installs both schemas in one immediate transaction; a schema-3 store preserves its prior rows and adds `vb_commits`, `vb_objects`, `vb_commit_objects`, `vb_refs`, `vb_operations`, and `vb_journal`. Foreign keys bind parent commits, refs and journal operations to the same profile; object references require existing commits and objects. Unique indexes prevent duplicate named refs and duplicate commit/object/role/page links, including null page IDs. The existing schema-3 checksum remains checked, schema 4 has its own checksum, and a damaged schema-4 table set is refused before write opening.

The normal profile metadata worker remains the sole production SQLite owner. There is no Qt-side SQLite connection or versioning write command. Private and ephemeral profile activation supplies no durable metadata path; a private `ProfileStore` open refuses before creating a file. This slice does not publish manifests, write objects, persist cookie values, or enable any production capability.
