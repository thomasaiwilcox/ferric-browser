# VB-059 — Visible-parent clean branch transaction

Status: verified for the scoped, test-feature visible-parent single-tab implementation. The original source view remains live, visible and usable in its original owner; it is not frozen or immutable. VB-098 separately gates hidden-parent retention. This slice status does not enable the production clean-branch capability or qualify every native fault path.

On 2026-10-07, the core lineage model was corrected to distinguish the parent profile's logical lineage namespace from the child's actual native application/profile owner. A clean child may now publish with a distinct `NativeProfileOwner`; root lines still require their exact original application/profile owner, and reusing the parent native owner fails without mutation. The focused core branch suite passed 23/23. The VB-058 Quick profile lease is prepared hidden and remains undiscoverable until an explicit publish call.

The application now prepares an exact single-tab structural fork and waits for durable commit completion before emitting a child-allocation request. It rejects a changed source target, logical page, profile generation, or native owner; failed commits and pre-publication aborts release the typed reservation. After the hidden child has bootstrapped, the Qt bridge checks a distinct child `BrowserUi`, its actual bound ephemeral application/profile generation, and its first tab. The application preflights the child lineage bind and parent root/branch events against disposable runtime copies before publishing them. The child receives a new logical page with its parent lineage; the parent stays live. Closing the exact child drops the branch and releases its Rust lease, while a stale child owner is rejected without mutation.

The prepared QML child rejects mixed private/ephemeral/shared-profile, transfer, restore, context and nonblank startup settings. It does not perform ordinary startup navigation; its WebEngineView URL binding stays at `about:blank` until admission. The root tracks a bounded hidden preparation and the exact QML profile/view lease. Only after native binding and lineage publication may a safe GET be queued; the child-side Rust method checks its ephemeral native owner and published lineage and returns the navigation enqueue result, allowing a failed enqueue to tear down the hidden child. Placeholder forks remain blank. Publication registers and shows the child only after all of those checks. The QML destruction callback closes or aborts the parent-side branch and releases the exact profile/view lease.

The user command route is available only with the explicit `unqualified-clean-branch-test` build feature; the default build still rejects it. `versioning.clean_branch` remains unqualified and production-disabled. The native observations below cover command-to-durable-fork-to-hidden-child publication, safe-GET navigation, POST and unsafe-URL placeholder behavior, and ordinary confirmed close. The exact QML failure decisions are exercised in the focused fixture; native fault injection for allocation timeout/failure and navigation rejection remains part of later production/release qualification. The durable structural commit is intentionally retained as a normal user commit if later child allocation or navigation fails.

Focused checks so far: the application branch suite (9/9, including stale-owner close, abort, POST-like proof invalidation and unsafe-URL assertions), default and test-feature command routes (1/1 each), the Qt boundary test `clean_branch_window_requires_distinct_off_record_profile_lease_before_navigation` (1/1), `tst_clean_branch_profile.qml` (5/5 including setup/teardown), and the native Quick profile/cookie-store probe. The Qt adapter check and a feature-enabled browser build passed after the navigation-result guard. Qt's QML parser accepts both changed window components (with existing cross-component lint warnings). These focused checks alone do not establish the native journey or production capability; the native observations below cover only the named subcases.

A disposable, offscreen feature-enabled Ferric process accepted `branch native-trial --clean`. Before the command, `query windows` showed one normal live registry entry and original `tabid-7`. After durable completion, it showed that same normal window/tab plus a second `ephemeral: true` window with a distinct owner token and one tab. This establishes one real placeholder child publication while the parent remains active. A targeted `window-close` command was acknowledged but correctly opened the ordinary confirmation path; IPC acknowledgment did not close the window. A further `tab-close` acknowledgment also did not prove teardown. An isolated headless Weston/accessibility attempt exposed the process tree but its Ferric instance would not answer window queries or branch commands, so that attempt is inconclusive. Neither run proves the close callback or failed-navigation cleanup. The three disposable test profile directories and isolated compositor were stopped and removed; no user's ordinary profile was touched.

A second disposable offscreen process navigated its original `tabid-7` to the project's loopback `/versioning/document` fixture. `query tabs --window active` confirmed that tab was `loading: complete` at the exact HTTP URL. The new test-fixture request counter read 1 before `branch native-counted --clean`, 2 after it, and remained 2. The parent live registry entry and tab ID stayed unchanged while another distinct ephemeral one-tab child appeared. Read-only inspection of the durable fork manifests showed two `replayable` descriptors, including this counted source URL. The extra exact-document GET after branch, from a child with a fresh off-record profile, is native evidence of a safe-GET child navigation; it does not claim a page-state clone or any cookie/storage inheritance. Both fixture servers and the disposable browser were stopped, and this fourth test profile was removed.

The normal compositor supplied the missing close observation. A fresh disposable normal profile opened one clean child; IPC `window-close` requested the ordinary child confirmation, and a process-PID-scoped AT-SPI action pressed only that visible dialog's “Close browser window” button. `query windows` then showed only the unchanged original normal window and `tabid-7`. A new `branch native-confirm --clean` using the **same name** opened a new distinct ephemeral child, which would be refused if the prior branch record still held that name. The second child also closed through its confirmation and left only the parent; the parent then closed through its own confirmation with process exit code 0. This is native evidence for the ordinary confirmed close/release path, though not for arbitrary nested descendants, failures, or hidden-parent retention. The test process and its disposable profile were removed.

An application regression now invalidates a same-URL typed GET proof to model a POST, then verifies that durable branch readiness carries an unsafe-navigation placeholder and the original source URL/target remains unchanged. The same test checks that a token-bearing URL cannot acquire typed GET proof and also forks only a placeholder.

A third disposable native process loaded the loopback document with `?token=synthetic`. Its original tab stayed loaded and live; the fixture's exact-document counter read 1. `branch unsafe-token --clean` published an ephemeral child while the counter stayed 1, so no token-bearing GET was replayed. Read-only inspection of the durable fork showed `placeholder / unsafe-navigation`; the parent window and `tabid-7` remained unchanged. The child and parent closed through their ordinary confirmations with process exit 0, then the fixture server and disposable profile were removed. The fixture now also counts accepted synthetic form-result POSTs, with a focused unit regression, but a native POST submit could not be driven through this compositor's WebEngine accessibility action; do not claim that journey passed. Native POST, native child-allocation failure and native rejected child-navigation teardown remain open. The production capability remains disabled.

The production QML hidden-child creation and publication decisions now call the same small `CleanBranchPreparation.js` helper as a new QML fixture. Its 7/7 checks cover thrown child allocation, wrong child identity, owner-publication failure and abort, rejected child navigation destroying the hidden child before window publication, failed window publication, and placeholder success without navigation. These are deterministic QML failure-path tests, not native fault injection or evidence that a failed Qt allocation leaves no undiscoverable object. The Qt adapter rebuild and test-feature browser build both passed after this refactor. A fresh offscreen disposable smoke accepted `branch refactor-smoke --clean` and showed the unchanged normal parent plus a distinct ephemeral one-tab child; the process/profile were stopped and removed. The production gate remains disabled pending broader qualification.

The initial accessibility-driven form submission was inconclusive, but a later fixture route performed a single delayed synthetic form POST without desktop input or remote debugging. A fresh disposable offscreen Ferric instance loaded the result page in original `tabid-7` (`loading: complete`, URL `/versioning/form/result`); the fixture's accepted-POST counter was 1. `branch native-post --clean` added a distinct ephemeral child while that counter remained 1. The durable fork manifest recorded `placeholder / unsafe-navigation`, and the parent window/tab identity was unchanged. The browser, server and test profile were stopped and removed. This closes the native POST no-replay observation for the scoped single-tab path. Native fault-injected allocation/navigation rejection and the broader release campaign remain open; `versioning.clean_branch` remains production-disabled.
