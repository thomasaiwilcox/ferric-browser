## Record and validation

`capabilities.json` is schema 1 and records the exact observed Qt, QtWebEngine, Chromium base/security-patch API and distribution package versions from the disposable VB-000 probe. It lists all ten planned feature capabilities with a primitive gate, separate production enablement flag, backend, scope, evidence IDs, stable reason code and human-readable reason. No capability is production enabled. The default public Qt backend marks general cookie identity, complete snapshots and controlled merge application unsupported; other unimplemented native paths remain unqualified.

`xtask` validates the record during its normal `check` path. It rejects an unknown schema, missing/extra capability fields, unknown feature names, invalid or missing fingerprints, and a caller-supplied fingerprint mismatch. A supported primitive requires a declared scope and evidence. A production flag requires a separate matching release certificate whose task is verified in the P8 ledger; changing the flag alone is rejected even after the live-retention primitive became supported. An extra `mirror_revision` field is rejected, so an observed mirror counter cannot be smuggled into this qualification record as an engine transaction boundary. The record contains no cookie values, URLs, page content or account identifiers. It is qualification metadata, not a runtime feature switch or native certificate.

The existing diagnostics path uses `qWebEngineChromiumVersion` and `qWebEngineChromiumSecurityPatchVersion` through the public Qt bridge; `runtime_facts.rs` publishes bounded version facts. `pkg-config` and the package manager provide the other observed fingerprint fields. A future native certificate must revalidate the exact engine fingerprint and scope before changing a gate.
