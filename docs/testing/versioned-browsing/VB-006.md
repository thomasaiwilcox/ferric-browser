## Fixture contract

The existing `cargo xtask fixture-server` owns a bounded loopback HTTP server. Its `/versioning/` catalogue now supplies a long document with two nested scrollers and expansion, a classic multipart form (including hidden token, password, file and OTP), model-controlled input, blur-autosaving contenteditable, freeze/resume handlers, mutation/navigation, same- and cross-origin frames with reorder/delete and open/closed shadow roots, polling/worker/service-worker/WebSocket activity, hostile archive actions, and synthetic login/CSRF/logout. `/versioning/fault/slow`, `/versioning/fault/error` and `/versioning/fault/close` provide bounded failure/cancellation conditions. There is no live account or Internet dependency.

The login fixture issues two related synthetic cookies. Its member and mutation routes require both cookies and current server state; mutation additionally requires the CSRF header/body. Logout revokes the server-side session and expires both cookies. This is a deterministic coupling fixture, not production authentication. HTTPS-only routes emit Secure/HttpOnly/SameSite/Partitioned headers, duplicate names at different paths, expiry/session variations and a `localhost` domain variant. The server does not claim that Qt preserves every attribute.

`--https` creates a one-day self-signed certificate and key under a 0700 disposable directory. The HTTPS mode is a loopback-only `socat` proxy to the existing fixture server; it prints the generated certificate path for a test client and removes the directory on graceful exit. The native probe uses an off-the-record public `QWebEngineProfile`, redirects XDG config/cache/data to its own disposable root, and accepts a certificate error only when the URL is the selected loopback HTTPS origin and the peer leaf SHA-256 matches the generated certificate. It does not change global trust settings or disable Chromium sandboxing. The disposable native root and certificate are verified absent after the probe. The public `QWebEnginePage::certificateError`/`QWebEngineCertificateError::certificateChain()` boundary is documented by [Qt](https://doc.qt.io/qt-6/qwebenginecertificateerror.html).

The native TLS probe explicitly prints `skipped/unqualified` if `openssl`, `socat`, `curl` or the Qt WebEngine Core development package is unavailable. Secure/SameSite/partitioned fixtures cannot run over the ordinary HTTP endpoint (HTTP 426). SameSite and partition identity are **not** native-qualified by this slice: VB-005 found that the public cookie callback loses those dimensions. Browser-side acceptance of the domain and partition variants is likewise unqualified. A missing prerequisite or an unqualified attribute is not reported as a pass.

## Privacy, ownership and remaining scope

All payloads are fixed synthetic strings. Request bodies and cookie values are not logged. The server validates loopback binding, caps request size and response assets, and closes after a selected test path or one request. The TLS certificate is trusted only by the disposable native probe after peer pin verification. Renderer termination and profile teardown while a future stash/capture callback is pending still require the later native feature harness; the slow/close/error fixtures provide deterministic pending and failure endpoints, but this slice does not claim a crash or feature-callback qualification. No private Qt API, copied profile, production account or external origin is used.
