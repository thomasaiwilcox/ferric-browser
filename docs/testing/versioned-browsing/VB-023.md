# VB-023 — Safe restore planning and fresh ID allocation

Status: verified for read-only planning; no restore execution is enabled.
Baseline SHA: `deea458d92bcf6d8fbea7b04af17823b5882cc1b`
Implementation SHA: uncommitted working tree atop the baseline.

The normal-profile worker has a typed, exact-ID manifest read for trusted application use. It applies the same pre-allocation byte limit, SHA-256, schema, owner, timestamp and object-link checks used by redacted commit info; the full manifest is not projected to Qt or IPC. An application ticket correlates the result and rechecks the current durable normal-profile owner before producing a plan. Closing/replacing a profile cannot leave a pending read attached to a new owner.

The planner refuses context scope and context references until their ownership semantics are implemented. It validates all stored logical IDs and the current safe URL policy, preserves unsafe or unobserved pages as explicit placeholders, and does not apply stored policies, history, form state, or lifecycle claims. It predicts fresh window/tab IDs by replaying ordinary reducer allocation on an isolated state clone and records the admitted revision. Execution must require that revision and confirm that the reducer allocates the predicted IDs; a new Qt window has its own reducer instance and must plan again at the destination rather than reuse source-window ID predictions. The plan itself changes no live window, tab, or navigation state. It records selected-first navigation order while leaving background navigation deferred. Duplicate URLs remain distinct logical pages and distinct planned runtime tabs.
