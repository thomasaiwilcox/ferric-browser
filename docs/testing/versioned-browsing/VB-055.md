# VB-055 — Add media metadata without automatic playback

Status: verified for the bounded implementation acceptance on the tested
Linux/GNOME Secret Service path. The keyed capture/restore path, fail-closed
key handling, profile-deletion cleanup, and no-automatic-playback boundary have
focused storage/QML and native integration evidence. The final workspace/release
gate, cross-provider and item-only-lock qualification, arbitrary-site media
qualification, remaining source-hint privacy review, and VB-057 integration
qualification remain open; production capture/recovery stays disabled.

## Implemented surface

- The one-use page-capture authorization and fixed native disclosure cover
  bounded media position and paused state. The current page helper bundle
  (`ferric-page-state-5`) records this as a separate sidecar category; no media
  API is called to start, stop, or resume playback.
- The collector omits media without a visible element, with an unsupported or
  non-finite duration, and known live, DRM, MediaStream, blob, or adaptive
  streaming sources. A bounded canonical source URL exists only in transient
  collector/native restore callbacks. Rust replaces it with a profile-keyed
  HMAC-SHA-256 before parsing or storing sidecar bytes. The fingerprint
  prevents an optional restore from seeking a different file in a same-looking
  element. It is a pseudonymous equality hint, not encryption or anonymization;
  it remains linkable within a profile and can be recomputed by a process able
  to access the unlocked Secret Service item.
- The open-live confirmation has a separate, unchecked-by-default opt-in for
  compatible paused media positions. If selected, only media paused both in
  the stored sidecar and in the current document is considered. The Rust
  planner requires the exact route, unique DOM identity, context, and source
  fingerprint. The ApplicationWorld helper rechecks the exact canonical source
  URL observed for the plan, plus the live element, duration, ready state,
  pause state, source type, and document, before one bounded `currentTime`
  assignment. The key never reaches ApplicationWorld.
- The UI warns that seeking may request network media segments. There is no
  `play()`, `pause()`, `load()`, microphone, camera, or screen-capture call in
  the media restore path; no saved paused state triggers playback.

## Remaining qualification

- Heuristics cannot identify every streaming or expiring-media scheme. The
  exact source fingerprint and paused-only rule narrow accidental mismatches,
  but do not establish that a site's playback semantics are reconstructible.
- The current keyed hint is still deterministic and linkable within one profile,
  and Secret Service does not promise app-specific access control or a prompt
  while items are unlocked. Review whether this narrower detached-sidecar
  threat boundary meets product policy; do not describe it as archive
  encryption, same-user isolation, or renderer protection. Keep page
  capture/recovery release gates closed until VB-057 qualification.

## Source-fingerprint security boundary — 2026-10-02

The media URL is an asset: its path or query can reveal private content or
bearer-like tokens. A sidecar-only reader can dictionary-test the current
stable `SHA-256("media-source:" || canonical URL)` value and correlate the
same source across captures. A same-account reader of the entire profile may
also read the private MHTML archive, so a keyed sidecar hint alone would not
provide archive confidentiality. The page already knows its own URL; the
meaningful boundary here is persisted sidecar bytes versus ordinary
Debug/UI/IPC projections and the separately opted-in restore helper.

Core regression coverage now requires the source hint to be absent from
`PageStateSidecar` Debug and its serialized safe summary, absent from a
restore request when media restore is declined, and present only in the
explicitly opted-in helper request. The focused core test and strict core
Clippy pass. This confirms projection containment, not secrecy of the
stored sidecar: its deterministic digest remains guessable.

No profile secret or key-custody lifecycle is present in the inspected
versioning path. A keyed replacement would need a reviewed secret
provisioned outside the sidecar, capture/restore availability, backup and
restart behavior,
rotation/revocation, failure handling and tests. The public nonce and capture
fingerprint are stored alongside the hint and cannot serve as secret keys.
Do not add an ad hoc key beside the archive or claim HMAC would make the
unencrypted MHTML private. The product/security decision is still open:
either explicitly accept the sidecar-only dictionary/linkability risk under
the archive's sensitive-local-data model, or design and review a real key
lifecycle before enabling optional media seek. Production gates remain off.

## Keyed-fingerprint feasibility recheck — 2026-10-04

The capture/restore boundary was traced again before considering a keyed
replacement. Capture hands the sidecar collector a one-use challenge from the
Qt adapter; restore separately builds the request in the application layer.
Neither path currently receives profile secret material, and the inspected
profile/versioning implementation contains no operating-system credential
store integration or key provisioning, backup, rotation, revocation, or
recovery contract. The public capture nonce and route/capture fingerprints
are persisted correlation values, not secrets.

An unkeyed value cannot be repaired by placing a random key beside the
sidecar/object store: a reader with the same profile-directory access could
read both. Passing a persistent key through the ApplicationWorld request
would also expand the trusted secret-handling boundary in both capture and
restore without solving custody or export/recovery. No such key was added.
The remaining feasible paths are an explicit security decision accepting the
existing sidecar-only risk, or a separately designed OS-protected profile-key
lifecycle with defined behavior when the key is unavailable. Until one is
approved, optional media restore remains gated; the existing local WAV
journey remains implementation evidence, not approval of the digest risk.

## OS credential-store feasibility recheck — 2026-10-05

The current declared product target is native Linux. Linux Secret Service is a
candidate external key store, and the Rust `keyring` API can store/retrieve
binary secrets while reporting when no default store is available. However,
the Secret Service specification explicitly does not require either a master
password or application access control; lookup attributes are also not secret
material, and whether a locked item prompts is service-specific. Therefore an
OS credential-store key could protect a detached sidecar from an offline
reader who does not also have the source user's session/key store, but cannot
be claimed to resist a same-user process that can access an unlocked service.
There is no silent plaintext/profile-file fallback.

A viable implementation would need an exact profile-scoped secret identity,
atomic first-use provisioning, bounded secret lifetime, a fail-closed outcome
when the store is absent/locked/deleted, no key in the sidecar or Debug/IPC,
and a narrow native fingerprint boundary. Existing capture and restore
helpers currently compute the digest inside ApplicationWorld; neither has a
key-store integration point. HMAC-SHA-256 is available as a standard keyed
construction, but adding it does not by itself solve key custody or local
same-user access. No keyring dependency or ad hoc key was added. Until the
product threat model explicitly accepts the narrower detached-sidecar
assumption or a stronger key-access mechanism is designed, the digest risk and
media-seek release gate remain open.

## Key-store integration boundary recheck — 2026-10-06

The current threat boundary is a detached sidecar reader who does not also
control the user's unlocked session. The media URL is still visible to the
page and to a same-user process that can inspect the running application; a
keyed source hint must not be described as archive encryption or protection
from a compromised renderer/process.

The current Rust `keyring` Entry API can get and set binary secrets, and HMAC-
SHA-256 is available from RustCrypto. Neither fact supplies the missing Ferric
integration: no key-store dependency or profile-key manager exists, the page
collector and final media recheck both run in ApplicationWorld, and the
existing Rust/QML callbacks are synchronous at the collector-request
boundary. Passing the key into ApplicationWorld would place key bytes in the
renderer process; moving the URL out to Rust for HMAC instead would expand the
transient URL-handling boundary and would need a new exact-document callback
protocol. A blocking Secret Service lookup must not be added to the GUI thread.

Secret Service's current draft permits a service implementation to allow
another client to access items unlocked by a different client; it does not
provide a cross-desktop promise of app-specific ACLs or a master-password
prompt. Therefore a keyring-backed HMAC could narrow detached-sidecar
dictionary testing under an explicit threat model, but cannot claim same-user
or running-process secrecy. Provisioning, locked/missing-store behavior,
cross-profile identity, backup/restart behavior, rotation/deletion, async
availability, and renderer-memory exposure need a reviewed design before
integration. There is still no plaintext/profile-file fallback, and no
production or release gate changed.

## Concrete Secret Service key-lifecycle route — researched 2026-10-07

The Linux path is technically implementable without putting a key in the
renderer or blocking Qt's GUI thread. `keyring` 3.6.3 exposes binary
`Entry::get_secret`/`set_secret` operations and an explicit synchronous Secret
Service feature. Its own documentation says these calls block and can take tens
to hundreds of milliseconds, so Ferric would route every key operation through
one serialized background worker. This checkout's research host has
`libsecret-1` 0.21.7, `secret-tool`, and an active
`org.freedesktop.secrets` service; this confirms local test availability, not a
requirement that every supported desktop provides it.

The proposed lifecycle is:

1. Use only the explicit Secret Service backend (no mock, keyutils, or file
   fallback). Bind the entry to a stable profile UUID and key-version ID, never
   a profile path or display name. Keep that non-secret ID in profile metadata;
   store 32 random key bytes only in Secret Service.
2. Provision only during an explicit media-capture operation, serialized
   under the profile owner lock. Restore is retrieve-only: missing, locked,
   ambiguous, malformed, or unavailable credentials suppress media matching
   and seeking rather than generating a replacement key.
3. Replace the renderer's deterministic SHA-256 with domain-separated
   HMAC-SHA-256 in native Rust. The key never enters ApplicationWorld. A new
   bounded exact-document callback must hand only candidate media URLs to the
   native path for hashing, then zeroize temporary buffers; the final
   pre-seek source recheck must repeat that route against the same document
   challenge so a changed element is still refused.
4. Persist an algorithm and key-version label with each fingerprint. Existing
   unkeyed fingerprints are legacy and must not be silently accepted or
   upgraded; when their source is unavailable, optional media seek is skipped.
   Key rotation changes the key-version ID; old media hints remain unusable
   unless a reviewed rekey operation is added.

HMAC is a reviewed keyed-hash construction described by informational RFC 2104
and available from the RustCrypto `hmac` crate; it must not be reimplemented in
JavaScript. The result remains deterministic within a profile and thus still
linkable across that profile's sidecars. The Secret Service API does not
guarantee a master-password prompt or application-level access control: an
implementation may allow another client to read an item that is already
unlocked. This route can narrow dictionary attacks by a detached sidecar reader
without the unlocked user session; it cannot claim protection from a same-user
process, a compromised Ferric process, or someone who also has the profile
archive.

Security review kept this as a proposed route: no real key was created or read,
no dependency or production code was changed, and no fallback was introduced.
The remaining gate is explicit: accept the narrow detached-sidecar threat
model, select a credential service with a stronger reviewed access-control
guarantee, or leave media matching disabled. After that decision, implementation
still needs the worker, profile-key lifecycle, native URL-hashing callbacks,
legacy handling and focused failure tests before VB-055 or VB-057 can be called
complete.

Primary references: [keyring 3.6.3 feature and threading guidance](https://docs.rs/crate/keyring/3.6.3/source/README.md),
[`Entry` binary secret API](https://docs.rs/keyring/3.6.3/keyring/struct.Entry.html),
[Secret Service locking and access-control contract](https://specifications.freedesktop.org/secret-service/latest-single/),
and [RFC 2104](https://www.rfc-editor.org/info/rfc2104/).

## Native keyed media path integrated — initial implementation 2026-10-07

The storage crate now contains a Linux-only `MediaFingerprintKey` primitive.
The initial version used the explicitly selected `keyring` 3.6.3 synchronous
Secret Service backend. A later source review found that its lookup path
unlocks matching locked items; the implementation has since moved to the
direct `dbus-secret-service` API so Ferric can reject locked state without
asking the service to unlock. The current adapter has no mock, keyutils,
plaintext-file, or environment fallback; it stores one versioned item under
the persistent profile UUID and serializes provisioning with Ferric's existing
cross-process exclusive `ProfileLock`. First-use provisioning reads back the
credential before returning it. Secret buffers use zeroizing containers, the
key's `Debug` view is redacted, and the fingerprint uses a domain-separated
HMAC-SHA-256 over a bounded HTTP(S) URL. The profile UUID and lock behavior
were confirmed in `ferric-browser-storage/src/profiles.rs`.

A durable, private state marker is written before first-use credential creation.
Profile deletion consults it before touching Secret Service, so profiles that
never opted into media capture do not acquire a new credential-store
dependency. A malformed marker fails closed; successful key deletion removes
and syncs the marker, while unavailable Secret Service preserves it alongside
the existing deletion manifest for retry.
The full Ferric data-reset path also deletes all marked profile keys before it
clears roots and refuses the reset if credential cleanup is unavailable, so it
does not erase the only retry markers while leaving a known key behind.
Reset first validates every owned root directory, so an already-unsafe root is
reported before any OS credential is deleted. The focused ordering regression
is authored but remains unrun with the other final checks.
The marked-key scan and key deletions hold the process-wide key-operation
guard, preventing an in-process capture or rotation from provisioning a key
after enumeration but before reset clears state. Cross-process reset still
depends on the application quiescing profile work before invoking the storage
reset API.
The marked-key scanner also refuses malformed profile identities before any
credential-store access; corrupted marker content remains present when cleanup
fails so it cannot silently lose retry evidence.

The primitive also exposes a load-only worker API for restore. A missing or
deleted key is not silently replaced during restore, which prevents a new key
from being mistaken for the key that authenticated an older sidecar.

Secret Service calls are synchronous and `open_blocking` explicitly requires
a worker thread. The page helper now sends a bounded canonical URL only in a
transient observation result; the native adapter converts eligible media
values to the profile HMAC before sidecar parsing/storage, or removes media
records when the key is unavailable. Restore requests load rather than replace
missing keys, wait for the worker, and leave media excluded if it cannot be
loaded. The restore helper rechecks the exact observed source URL immediately
before seeking. No key reaches ApplicationWorld. No credential was accessed
or written during this implementation pass; the added HMAC, marker, legacy,
and normalization tests are deferred
to the final verification phase. Profile deletion now removes the Secret
Service item after registry commit; if the store is unavailable, the existing
deletion manifest remains for a later cleanup retry. Persisted keyed hints
carry the `hmac-sha256-v1-kN:` label and lowercase 64-character digest. Legacy
unkeyed values and unknown future versions remain parseable so unrelated
sidecar categories survive, but only the active supported format can authorize
a media match. Each persisted hint has a `hmac-sha256-v1-kN:` label; the active
key epoch is held in the private state marker and Secret Service item identity. An
explicit worker-thread rotation removes the old item, advances the epoch, and
provisions a new key without rekeying sidecars. If the active item disappears,
restore only skips media; the next explicit capture advances to a fresh epoch.
Rotation and profile deletion revoke earlier in-process key instances, and the
Qt adapter refuses to fingerprint with a stale cached instance.
Old media hints remain intentionally unusable, while other sidecar categories
remain recoverable. Before release, exercise locked, missing, malformed,
unavailable-store, rotation-interruption, and deletion-retry cases. Keep
the threat boundary narrow: this can reduce
detached-sidecar guessing only when the reader lacks the unlocked user session;
it does not protect against a same-user process or a reader with the archived
MHTML.

## No-prompt Secret Service adapter and isolated qualification — 2026-10-07

Review of the exact pinned `keyring` 3.6.3 source found that its Secret Service
lookup helper iterates locked matches and calls `Item::unlock()`. Its default
prompt timeout can wait for user interaction, which is not acceptable for
Ferric's worker-backed, fail-closed key lifecycle. The implementation now uses
`dbus-secret-service` 4.1.0 directly with an encrypted DH session and a zero
prompt timeout. It checks that the default collection is unlocked, rejects
locked or ambiguous search results, and never calls an unlock operation. A
locked item/collection or an operation that would need authorization becomes
an unavailable-store error; it cannot block waiting on a desktop prompt.
Secret Service item lookup attributes remain compatible with the prior
`keyring` identity (`target`, `service`, and `username`).

session and temporary XDG data/config directories, starts GNOME Keyring only
inside that session, and bounds each cargo test process to 30 seconds. Its two
ignored production-adapter journeys passed 2/2: provision, read back, rotate,
verify key revocation and profile separation, delete, then lock the default
collection and require load/deletion refusal while the collection stays
locked and the cleanup marker remains; separately, replace the test process's

This qualifies the current direct adapter against the local GNOME Keyring

[pinned `keyring` 3.6.3 source](https://docs.rs/crate/keyring/3.6.3/source/src/secret_service.rs),
