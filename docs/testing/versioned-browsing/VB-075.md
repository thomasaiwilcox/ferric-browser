# VB-075 — Destination seed and read-back contract for supported fixtures

Status: verified for the synthetic qualified-backend contract; no production Qt seed capability
Baseline SHA: `deea458d92bcf6d8fbea7b04af17823b5882cc1b`
Implementation SHA: uncommitted working tree atop the baseline
Affected requirements: `VERSION-005`, `VERSION-006`, `VERSION-009`; invariants `VB-I06`, `VB-I07`, `VB-I12`, `VB-I17`

## Contract and outcomes

`CookieSeedPlan` accepts only a complete, consistent, lossless source read with evidence matching an exact backend/scope. It bounds the seed to 256 records, refuses non-present and already expired entries, and supplies an explicit canonical HTTPS origin for each exact record. The in-memory plan carries the full `CookieRecord`, including raw value and backend identity/attributes, without serializing or logging it. Destination admission independently checks engine build, identity version/dimensions, supported attributes, exact read-back, exclusive apply and write support. It requires a distinct prepared owner and an untouched, un-navigated destination before any write.

`seed_prepared_destination` consumes that destination. It dispatches the exact records, checks cancellation/navigation, and requires a fresh destination-owner-bound complete read whose entire snapshot equals the source. Dispatch success or arbitrary cookie notifications are never transaction completion. `Seeded` returns the destination for navigation; a rejected write or cancellation returns `Failed`; missing read acknowledgement, changed attributes, wrong owner or navigation returns `Unverified(CookieSeedUnverified)`. Every failure/unverified path invokes `destroy`, so the prepared child cannot be silently released as a partial or clean branch. The backend implementation must provide the asserted exclusive ownership and fresh exact read; the application does not infer these facts from a Qt callback.

The positive fixture backend exists only in Rust unit tests. It retains records and returns a separately qualified exact destination read; tests exercise success, missing acknowledgement, rejection, expiration, SameSite attribute drift, cancellation and wrong-owner read-back. A public-Qt-capability destination is rejected before dispatch even when supplied a synthetic qualified source. The production `qt_public` capability still reports lossy identity, observed-only snapshot/read-back and no exclusive apply. VB-073 and VB-074 native findings prevent claiming a production seed certificate. The native adapter was inspected but not wired as a `CookieSeedDestination`: its public callbacks lack exact read-back and cannot satisfy this contract.

Subsequent isolated engine research found a feasible *different backend path* for two disk-loaded edge records: a source-pinned seed-if-empty overlay passed three fresh 40-check runs with exact in-process canonical read-back, native two-record restart evidence and nonempty-child refusal. See [engine-capability-spike.md](engine-capability-spike.md) and `tools/versioning-engine-spike/source-lock.json`. That experiment is not the `CookieSeedDestination` implementation above: it lacks a source-T0 ownership handle, an exclusive child writer lease, a status-bearing durable commit and failure cleanup. Qt's ordinary `cookieAdded` name signals were not observed on restart. Keep production seed capabilities disabled and VB-076 blocked until a reviewed backend meets the full contract.

A separate disposable post-snapshot-write fixture subsequently passed three fresh runs: it forced a third source cookie after the native two-record callback but before seeding, then found source three and child two by independent exact copies. This supports a scoped point-in-time cut; it still does not bind that cut to a Ferric owner generation or exclude concurrent writers, so it does not change the production capability decision.

Another disposable fixture tested a fresh child with no application page. Calling `cookieStore()` alone left its native CookieManager unavailable. A source-pinned research hook initialized only the child's storage partition and browser-process cookie manager; three fresh 46-check runs then seeded both disk-loaded edge cases exactly before creating any child page, found two records after page creation, and found two after normal-close restart. The 40/53/33/59/59 native regressions passed. This narrows the child-writer surface, but it does not establish an exclusive store mutation lease, no competing browser-process writer, source-owner generation, or crash-durable publication. Production seed capability remains disabled.

Three additional disposable campaigns exercise source/destination owner loss on those two disk-loaded control variants. Destroying the exact destination profile before its async copy reply routes yields exactly one `OwnerLost`, and the source then copies exactly to a fresh off-the-record control. Destroying the exact source profile while a reply is pending also yields exactly one `OwnerLost`. Each campaign passed 32 checks; a possibly mutated destination is discarded. The fixture, engine, runner and binary hashes are recorded in `source-lock.json`. This does not prove Mojo service disconnection, source-generation binding, destination writer exclusion, crash durability, or the full `CookieSeedDestination` contract; production seed remains disabled.

A follow-on source-pinned experiment now disconnects the bound CookieManager Mojo receiver while GetAllCookies is pending. Three source-loss and three destination-loss cases each returned exactly one TimedOut completion (54 checks total); source loss reported zero counts, while destination loss left the child count unknown and the child was discarded. The cookie, legacy/older-expiry, HTTPS, and current RTC regressions passed. This closes the specific disconnected-pipe callback question for the tested native path, but it does not model network-service process crash/restart, writer exclusion, source generation, durable publication, or exact destination read-back. It does not meet the CookieSeedDestination contract and does not unblock production seed; see the experiment record and artifact digests in engine-capability-spike.md and source-lock.json.

A 2026-10-06 read-only audit of the pinned Chromium writer paths found a
candidate interlock seam: `CookieManager::SetCanonicalCookie`,
`RestrictedCookieManager::SetCanonicalCookie`, and HTTP response `Set-Cookie`
all reach the shared CookieStore/CookieMonster setter. Delete/clear/session
cleanup operations use separate store methods, so a production lease would
have to gate every mutation on the store sequence, not just the public
CookieManager wrapper. This is a source-backed design lead, not an implemented
or exercised lease. The page-free unpublished-child seed route remains the
narrower prototype candidate; the current fixtures do not prove all internal
writers absent or provide durable-publication status. Production seed remains
disabled and VB-076 blocked.

## T0 write ordering follow-up — 2026-10-07

The disposable source-boundary fixture now performs an acknowledged synthetic
cookie write before requesting the native snapshot, then the test-only engine
overlay inserts another source write after the complete-list callback but
before seeding the child. Three fresh runs passed eight checks each. The child
read-back contains exactly the original two plus the pre-cut write; an
independent source copy sees the additional post-cut record, while an
independent child copy remains at three. Logs contain only fixed labels and
counts, not cookie values.

This is a controlled serial ordering witness, not simultaneous cross-interface
writer exclusion, exact Ferric source-generation ownership, exclusive child
writers, crash-durable publication or full `CookieSeedDestination` evidence.
No production capability changed; see `native_t0_pre_and_post_cut_followup`
in `tools/versioning-engine-spike/source-lock.json` for hashes.

## Public writer during copy orchestration — 2026-10-07

The same disposable fixture dispatches a multi-step public
`ferricCookieCopyExistingProbe` and, before pumping the Qt event loop again, a
public `QWebEngineCookieStore::setCookie` for a fixed synthetic record. The copy
probe performs source and destination preflight reads before its actual
complete-list request, so the setter can complete during that orchestration.
Three fresh runs passed eleven checks each. In all three, the new record was
present in the captured five-record cut and a later independent source copy
also returned exactly five. The fixture accepts either four or five at capture,
but these runs demonstrate a writer dispatched during preflight being included
when it completes before capture. Logs expose fixed check labels and counts,
never cookie values.

This does not race a public setter against the actual `GetAllCookies` request or
mutate while CookieMonster traverses its single-sequence maps. The pinned source
audit below supports sequence-point capture for that internal route, but this
fixture itself only proves writer-before-cut behavior during orchestration; it
does not establish a Ferric source-generation lease, complete writer coverage,
child-writer exclusion, or crash-durable publication. Production cookie
capabilities remain disabled. Fixture, runtime and run digests are recorded
under `native_t0_copy_operation_writer_followup` in
`tools/versioning-engine-spike/source-lock.json`.

## Pinned engine source-path audit — 2026-10-07

The pinned Qt/Chromium implementation narrows the concurrency question. Qt's
internal `CookieManager::GetAllCookies` forwards to
`CookieStore::GetAllCookiesAsync`; Chromium's `CookieMonster::GetAllCookiesAsync`
enters `DoCookieCallback`, and the implementation checks its owning thread,
expires stale ordinary and partitioned records, copies both maps into a
standalone `CookieList`, and only then invokes the callback. The inspected
set/delete paths also enter CookieMonster on that checked sequence. Combined
with the public-writer-during-preflight fixture, this is evidence that the
captured list represents one sequence point for the tested profile; the fixture
does not itself race a setter against the actual snapshot request.

This is source inspection of the source-pinned private bridge, not a public Qt
contract or an independently verified complete inventory of every browser
writer. Qt's public `QWebEngineCookieStore` still has no complete-list callback;
the native probe reaches internal Qt/Chromium objects. The code audit therefore
supports the snapshot mechanism's feasibility but does not provide Ferric
profile-generation binding, durable publication, the full source/destination
writer lease, or approval to ship a maintained Qt fork. Exact audited source
file digests are retained with the probe in `source-lock.json`; production
cookie capabilities remain disabled.

## Boundary

No real profile, account, cookie database or external site was read or written. No cookie value enters UI/IPC, logs, persistence or `Debug`. A real backend must first provide a reviewed source boundary, lossless identity/attribute conversion, an exclusive fresh destination and exact read-back. Until then `versioning.cookie_identity`, `versioning.cookie_snapshot` and `versioning.cookie_seed_verify` remain unsupported and VB-076 cannot enable snapshot-isolated branching.
