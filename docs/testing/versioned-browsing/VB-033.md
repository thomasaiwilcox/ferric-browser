# VB-033 — Single-tab stash preparation and freeze acknowledgement

Status: blocked (native host primitive, logical fallback reservation, exact application stage/rollback protocol and Rust-held native callback ticket exist; end-to-end stash cannot be safely admitted without a qualified per-view activity observation)
Baseline SHA: `deea458d92bcf6d8fbea7b04af17823b5882cc1b`
Implementation SHA: uncommitted working tree atop the baseline
Affected requirements: `VERSION-002`, `VERSION-009`; invariants `VB-I02`, `VB-I03`, `VB-I10`, `VB-I11`, `VB-I16`, `VB-I18`

## Implemented so far

The same-profile native view host can stage an exact view only after a distinct, visible same-profile fallback view exists. Staging hides and reparents the original under its long-lived creation owner without claiming a completed stash. The host requests `Frozen` only while Qt recommends it, and commits a retained record only after the *actual* `lifecycleState` reports `Frozen`. It rejects duplicate/late acknowledgement, duplicate registration, changed tab/profile/view identity, and a changed navigation epoch. Cancellation restores the original visual parent, visibility and enabled state and requests `Active`; ordinary tab removal/transfer refuses to destroy a staged view. The runtime view increments its native navigation epoch on each load start.

Core now projects an ordered visible tab strip that excludes reducer-owned retained/transferring/closing records without deleting their logical tabs. The runtime and application expose that read-only projection; the Qt adapter uses it during tab reconciliation and refuses to publish a projection with a retained tab still selected. After QML obtains its actual `WebEngineProfile` instance and finishes profile bootstrap, it binds one opaque native-profile lifetime to the application coordinator. Repeated adapter binding is idempotent; QML checks that the view host owns the same profile object. This supplies identity for later admitted operations but grants no stash authority.

The reducer can now prepare a retained view for a `StashId` without creating a synthetic branch. A retention record has exactly one branch or stash owner; preparation rejects duplicate stash IDs, duplicate tab ownership and stale document/owner facts. Acquiring the record changes visible membership and both lease counts together; exact release restores projection.

After exact native consent, the application can reserve that visible source record and open a distinct blank logical fallback. It returns runtime effects for the adapter to materialize the fallback and keeps a bounded operation-owned reservation. Failed allocation releases the visible source record; explicit abort releases it and closes only an unchanged blank fallback, preserving a fallback that has navigated. No Qt fallback-instance acknowledgement is connected yet, and the application does not claim that freeze succeeded.

Pre-stage reservations also clean up through ordinary operation cancellation, fail-before-execution, deadline expiry, native-owner replacement/close, and application-profile close. These application methods now return both coordinator and runtime effects together; a failed reducer cleanup is reported by exact operation ID rather than silently discarded. Owner close refuses to discard a binding while its reservation cannot be cleaned.

The application can now atomically issue one exact, non-serializable stage ticket after the preparation's runtime effects have been taken and the captured source and blank fallback are rechecked. Issuing a ticket still leaves core membership visible and acquires no profile/view lease. Cancellation or expiry after stage start returns a ticket-scoped native cleanup effect and records that native restoration is pending, distinct from an unexpected reducer cleanup failure. Profile close/rebind refuses to discard that owner. Only after a trusted, exact rollback acknowledgement does the application release the prepared record and unchanged fallback; duplicate/early acknowledgements cannot release it. The application tests model this callback boundary, but do not yet prove that a Qt host actually restored a view.

The native host can now undo a *successful native freeze acknowledgement* if the later application commit is refused. `restoreRetainedStash` accepts only the exact staged-stash view and ID, never a general retained view; it restores the original live QObject to its presenter and requests `Active` without destroying or reloading it. This is a native recovery primitive, not yet an integrated application rollback callback.

The host now keeps a bounded restoring entry after either prepared-stage cancellation or refused post-freeze publication. Reparenting and requesting `Active` alone never releases that native protection. `acknowledgeRestoredStash` checks the exact QObject, profile, tab identity, original presenter and actual `Active` lifecycle; it removes the native entry only after the trusted application cleanup callback returns `true`. A false or throwing cleanup keeps the entry for retry. `completeFrozenStash` invokes its commit callback only after the host observes the actual `Frozen` property. A literal `false` starts restoration; an exception or non-boolean callback result is treated as uncertain and retains native ownership. A successful callback marks the record committed, after which rollback is refused and the fallback becomes an ordinary tab. These are still host-only callback tests, not proof that the Rust adapter has supplied a real operation.

Core now has one exact `ConfirmFrozenStash` reducer event, which changes prepared visible/active membership to retained/frozen and acquires both leases atomically. `RollbackFrozenStash` returns that exact stash/view/owner to visible/active zero-lease state before publication. The application has a conditional success path for a trusted native `Frozen` acknowledgement: it rechecks the exact staged ticket, captured source, blank selected fallback, owner, deadline, configuration and prepared record; only then does it apply the atomic reducer transition, reconcile the coordinator callback, and publish completion. If coordinator publication is refused after the reducer transition, it rolls that transition back and leaves the stage pending for native restoration. Terminal rollback acknowledgement can also undo a core-frozen record after the native view has been restored. The tests model those callback preconditions; no QML-to-application callback is connected yet, so this is not proof of an end-to-end stash.

The Qt adapter now holds one exact, non-serializable application stage ticket in Rust. Its QML-facing callback accepts only the matching native view ID after the host observes `Frozen`, and maps a committed application transition, known refusal, or uncertain rollback to distinct host outcomes. After the host observes the original view back at `Active`, a second callback retries application cleanup while preserving the ticket and cancellation effects if cleanup fails. QML lifecycle signals route those callbacks through the host, and the adapter bounds coordinator-effect wakeups with an explicit rescan-required flag on overflow. The Rust tests model the application boundary; they do not exercise a real host-to-application stash.

The native host now emits a restoration notification after putting the original view back in its presenter. The runtime queues a reconciliation check for this notification as well as listening to lifecycle changes. This closes the already-`Active` cancellation race, where no lifecycle-change signal is guaranteed, and also retries a callback that ran synchronously before reparenting finished. The queued check still requires the actual `Active` state and the host's exact restoration guards; it is not a synthetic lifecycle acknowledgement.

The adapter now has a bounded maintenance path for a *registered* stage ticket: it expires overdue application operations, recognizes only the matching terminal operation, and returns that stage's exact native view ID for restoration. The QML host accepts an idempotent cleanup request for a prepared or uncommitted-frozen entry, but refuses an unknown or committed stash. Repeated polls keep the Rust ticket and native restoring entry until actual `Active` and trusted rollback acknowledgement. This closes the terminal-cancellation wakeup gap for a stage that has already been registered; it does not yet start a stash operation or install that stage from a user request.

The native host's preparation call now takes the fallback tab ID from the admitted reservation separately from the candidate fallback `WebEngineView`. It refuses a distinct same-profile view bearing a different tab ID, an empty ID, or reuse of the source ID before moving the source. This closes a host-side identity gap but does not materialize or attest the application fallback.

A new runtime preparation seam first reconciles the application's visible-tab projection into native views, then asks the host to resolve the exact source and selected fallback from that complete projection. The host rejects misaligned or duplicate tab/view IDs, a non-selected fallback, a missing view, and a fallback already navigating or no longer blank before moving the source. This seam is not yet invoked by an admitted stash operation; it is native pair validation, not a successful application-to-QML handoff or freeze.

The host now also exposes a read-only native-pair check that leaves the source visible. The Qt adapter can hold one exact admitted `StashPreparation` in Rust, hand its runtime effects to the caller, and expose only the view/source/fallback IDs to QML. Runtime reconciliation uses the read-only check before acknowledging materialization; failure requests application cancellation. The Rust acknowledgement rechecks the live logical source, selected blank fallback, owner and operation state, rejects a wrong or duplicate view ID, and retains the preparation for a later fresh eligibility check. Pre-stage expiry polling drops the bridge slot only after logical cleanup is resolved. A modeled test takes an acknowledged preparation and issues one Rust stage ticket, but no production `Start` consumer installs the preparation yet. This is not an integrated freeze.

The Rust adapter now has a bounded claim for an admitted stash `Start` effect. It checks the exact coordinator kind, owner, window, native-profile lifetime and captured target, holds one claim, and can advance it to validation only if that logical target is still live. It can explicitly fail a stale claim before mutation. A dropped queue wakeup is recoverable by scanning bounded requested coordinator operations. This claim itself grants no native activity observation or consent.

The QML runtime now polls that exact claim after normal work, resolves its admitted source tab through the current visible projection and a read-only native-host identity check, and then either acknowledges the same operation into `Validating` or fails it before mutation. The host rejects a mismatched or duplicate projection, foreign profile/host, missing source, occupied native stash entry, loading source or non-`Active` lifecycle; it does not use current focus as a substitute. A bounded native maintenance timer remains active while coordinator operations are live and expires an abandoned validation. This connection has not been exercised by a real admitted Rust-to-QML stash operation, and it supplies no categorical activity evidence or consent.

A disposable native probe now establishes a negative activity boundary: a connected, open local WebRTC data channel remained open while its hidden `WebEngineView` reported `recommendedState == Frozen`. Qt documents that property as an aggregate lifecycle recommendation, not a per-WebRTC connection report ([Qt lifecycle documentation](https://doc.qt.io/qt-6/qtwebengine-features.html#the-lifecyclestate-and-recommendedstate-properties)). Therefore the adapter must not infer `live_call: Clear` from a Frozen recommendation. The application continues to reject `Activity::Unknown` for live calls; no public native source for an exact per-view live-call absence proof has yet been qualified. This does not negate the already-qualified same-profile retention primitive, but prevents calling the current stash admission path safe or complete.

Qt's documented [WebEngine permission state](https://doc.qt.io/qt-6/qwebenginepermission.html) is per origin and records whether access was granted or denied; it is not a report of an active peer connection on this view. A data-only WebRTC channel requires no camera or microphone permission. This is an inference from the documented API and the local data-channel probe, not a claim that every possible public integration was exhausted. The adapter continues to leave the live-call category unknown.

The Rust adapter can now hold one exact application-created volatile-work preview and the non-serializable native decision sink in its native bridge. Registration requires the bound native-profile lifetime and a trusted categorical observation; only the redacted preview projection is returned. A wrong-operation acceptance cannot consume it. A trusted acceptance attempts the application one-use proof and rechecks a fresh observation before advancing to `Preparing`; replay is refused. If that recheck fails, the acceptance cannot be retried, but the exact operation remains available for dismissal or deadline cleanup. Decline cancels only the matching operation.

The native chrome now has a fixed-copy volatile-work dialog driven by a read-only Rust projection of that exact pending preview. It displays no page text, plan ID or confirmation permit. Escape and the safe action dismiss only the displayed operation through the revision-aware adapter path; QML cannot construct a permit. The approval action is intentionally disabled in production because no qualified per-view activity observation can yet be supplied on acceptance. The QML fixture verifies safe focus, disabled approval, exact callback ID and one-use dispatch; the Rust fixture verifies fixed copy, exact operation matching and continued dismissal after a failed acceptance. The consent methods were split into a dedicated module to keep the Qt implementation below the repository's 1,000-line budget. This is not a usable stash path or a real native consent-to-freeze test.

Consent registration, display and acceptance now also require the exact admitted source window, not merely a matching native profile. A modeled second-window regression in the same profile refuses registration and display there and leaves the first window's preview intact for a later exact acceptance. It prevents the dialog from following a focus/window switch but does not supply missing activity evidence.

A Rust-only consent-to-reservation seam now consumes the exact preview and, after the application accepts it, requests one logical fallback reservation. It holds the resulting preparation in the native bridge and returns the pre-mutation revision with the runtime effects required to present the blank fallback. A bridge refusal after application preparation cancels that same operation and returns its cleanup effects; the original source remains visible in core. No production UI caller can supply the trusted fresh observation yet, and no effect from this seam is presented to QML in the fixture, so this is not an end-to-end stash.

A second Rust-only handoff now consumes an exact, natively acknowledged fallback reservation after checking a fresh categorical observation. The application issues the stage ticket and the adapter holds it before returning only the exact native view/source/fallback routing IDs. A changed live-call activity category cancels the operation before any native freeze request, returns cleanup effects and leaves the source visible. Wrong operation IDs cannot consume the reservation. This assembles the adapter side of the freeze request but does not attest a real native observation or exercise the QML host across this boundary.

A native identity hold now covers the interval between fallback acknowledgement and a Rust stage ticket. It captures the exact source and fallback QObjects and source navigation epoch while the source remains visible and Active, protects them from ordinary tab removal, and permits a matching later preparation only against the same objects and document epoch. If the fallback changes or the source navigates before hiding, the hold remains available for the terminal cleanup request: the host moves the same source into its restoring protocol, then requires observed `Active` and a successful application cleanup callback before releasing native ownership. An untouched pre-ticket hold can instead be released without claiming a stage rollback. The runtime's stage preparation helper now requires this hold. No production `Start` path reaches the hold or stage yet, so the host test proves a native recovery primitive, not an integrated rollback.

The runtime materialization path now installs that exact native hold after the Rust fallback acknowledgement and before any stage ticket can be requested. A failed read-only check or failed hold aborts the still-visible logical reservation. A materialized bridge entry is no longer discarded merely because the operation became terminal: maintenance returns its exact held-view ID for native restoration, and only the host's observed-`Active` callback lets Rust release it. The application can retry a terminal, unstaged logical release under the same view/operation identity; a failed release leaves the bridge and native restoring entry for the next bounded tick. QML reconciliation refuses to destroy a view still protected by a held/prepared/restoring entry and runs again after successful host acknowledgement. An already-Active view is rechecked on each cleanup tick so a failed logical callback does not require a second lifecycle signal. These are independently tested application, adapter and host boundaries, not a cross-boundary stash operation.

The adapter now requires a one-use, exact-view acknowledgement after the QML host installs its native hold; materialization alone cannot issue a Rust stage ticket. If a fresh categorical eligibility check refuses after consuming the preparation, Rust retains the operation/view pair as a terminal cleanup route and blocks a new stash start until observed-`Active` restoration is acknowledged. A failed Rust hold acknowledgement cancels the logical reservation but likewise retains the materialized bridge entry for exact native cleanup. The stage/refusal tests model this boundary, including wrong/replayed acknowledgements and a wrong-view restoration refusal. Production still cannot reach this stage because the trusted activity observation and consent-to-reservation wiring are absent.

This is not a user-facing stash path. No production scheduler yet connects validation to the reservation bridge, obtains trustworthy categorical eligibility after native materialization, or calls the new Rust stage handoff before asking the host to freeze. Production remains disabled.

## Remaining acceptance work and blocker

VB-033 still requires a trustworthy categorical native observation to register the preview from an admitted operation and recheck it on consent; only then may the dialog approval action be connected. It also requires actual Qt presentation of the admitted/consented preparation's runtime effects, a trustworthy fresh categorical source observation before native staging, and calling the Rust stage handoff before the host's freeze request. The local WebRTC counterexample means a Frozen recommendation cannot satisfy the live-call category; an exact trustworthy activity source or an explicitly limited/refusing policy still needs qualification. The new `Start` routing itself still needs cross-boundary exercise from a real admitted operation. Tests still need actual freeze refusal, duplicate/late callback and navigation across that boundary. A native fixture must prove the integrated path retains the original instance without reload. The read-only source and materialization handoffs are not that end-to-end proof.

Blocker: the inspected public `WebEngineView`/`QWebEnginePage` activity and lifecycle APIs provide no qualified per-view proof that an active WebRTC data channel or call is absent. [Qt's lifecycle documentation](https://doc.qt.io/qt-6/qtwebengine-features.html#the-lifecyclestate-and-recommendedstate-properties) describes `recommendedState` as an aggregate recommendation, and the synthetic local connected-data-channel probe recorded `Frozen` while the channel was open. The [QML permission API](https://doc.qt.io/qt-6/qml-webenginepermission.html) reports per-origin permission requests, not active peer connections; the same native data-only channel opened with zero `permissionRequested` signals. Thus neither recommendation nor permission callbacks can establish the source's `live_call: Clear` category, which remains `Unknown`, and the application must refuse admission. This does not revoke the separate, qualified same-profile retention primitive. Unblock only with a public, exact per-view activity source and native counterexample tests (including data-only WebRTC), or an explicitly approved policy/architecture change that still meets the no-hidden-call invariant. Do not route a production freeze through a synthetic observation.

Public-API audit (2026-09-29): this checkout uses Qt / Qt WebEngine 6.11.2. The public `QWebEnginePage` reference exposes lifecycle, visibility and recent-audio state, but no peer-connection or ICE-connection state; the installed public Qt WebEngine headers likewise expose no active-WebRTC observer. The only WebRTC-named public setting found is `WebRTCPublicInterfacesOnly`, which restricts interface exposure and is not a connection-state report. This audit is corroborating evidence, not proof that no future Qt release will add such an API. References: [QWebEnginePage](https://doc.qt.io/qt-6/qwebenginepage.html), [Qt WebEngine lifecycle API](https://doc.qt.io/qt-6/qtwebengine-features.html#the-lifecycleState-and-recommendedState-properties), and the installed public headers under `/usr/include/qt6/QtWebEngineCore` and `/usr/include/qt6/QtWebEngineQuick`.
