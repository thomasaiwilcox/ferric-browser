# M0-02 / M0-03 implementation evidence

Date: 2026-09-19  
Status: in-progress

## Task card

- Requirements: M0-02, M0-03, ARCH-001, ARCH-003, ENGINE-001, WL-001.
- Files: `crates/browser-engine-qt`, `crates/rustbrowser`, and `qml/Main.qml`.
- Observable result: a CXX-Qt 0.10.0 bridge registers a Rust-owned QObject in
  a static QML module. The QML window composes native Qt Quick controls with a
  public `WebEngineView`; address, back, forward, reload, status, and accessible
  labels are present. Initial command-line input is supplied to QML through
  `QQmlApplicationEngine` initial properties, then resolved by the single
  live `browser-core` reducer owned by the Qt object and emitted as a typed
  navigation effect. The Qt object owns a live `browser-core` profile/window/tab
  reducer state: navigation,
  same-document URL, commit, complete, failure, history, reload, stop, and
  mode callbacks are reduced against captured targets. The main window exposes
  a reducer-backed tab strip and one persistent `WebEngineView` per tab, with
  indexed callbacks so background-tab navigation cannot overwrite selected-tab
  chrome. URL, title, load state,
  and view-lifetime facts are also mirrored into the Qt object from public QML
  engine signals. Engine `newWindowRequested` requests pass through the core
  gesture gate; accepted requests are adopted by a popup `WebEngineView` using
  the opener's explicit profile. `--temp-basedir` selects a private core profile
  and an explicit off-the-record `WebEngineProfile`.
- The address fields use a separate redacted display value: credentials,
  obvious secret query keys, and fragments are omitted, while bidi/control
  characters are rendered as visible placeholders; the internal navigation
  URL remains distinct from this browser-chrome presentation. When chrome
  width is constrained, the primary and secondary address fields preserve the
  full safe origin and elide only the path/query tail; focusing either field
  restores the full safe value for editing, and accessibility exposes that
  full safe value through the description. Sanitized path/query text is also
  wrapped in Unicode bidi-isolate controls so it cannot visually reorder the
  scheme or authority.
- The primary, secondary, and popup compact status bars share bounded activity
  formatting: profile/context identity, HTTPS versus HTTP transport (without
  implying website trust), loading progress, audible/muted state, pending
  permission, capture, download lifecycle and received-byte count, the active
  Site Doctor experiment, and per-tab blocked-request count. Inactive activity
  fields are omitted, while private and ephemeral profile identity remains
  textual.
- Build exit criteria: met. The crate compiles against the installed Qt 6.11.2
  distribution and the QML resource is registered by CXX-Qt.
- Runtime smoke: `QT_QPA_PLATFORM=wayland target/debug/rustbrowser
  --temp-basedir` remains alive under the active Wayland session for a timed
  probe with no QML load errors; the command is intentionally terminated by
  the timeout after the event loop starts.
- The bounded offscreen adapter harness also passed on 2026-09-19:
  `cargo xtask test adapter`.

## Limitations

The GUI object currently owns a per-window reducer instance; sharing that state
with the process-level bootstrap and routing returned effects through a typed
engine adapter remain open. Same-profile live tab reparenting is now wired for
the primary and secondary browser-owned windows, with stable target validation,
transfer cleanup, and reducer acknowledgements; cross-window and popup
qualification remain open. Primary and secondary durable windows now derive
their QtWebEngine storage namespaces from the selected validated profile name,
and custom `--basedir` launches place persistent WebEngine data and cache under
that base. Live two-profile cookie-isolation qualification remains open. Compositor-visible
window inspection, popup close/opener lifecycle, and lifetime fault injection
also remain open. Main-window tab close now exercises the reducer
acknowledgement path; popup-window close remains separate.
Help/version continue to avoid creating a display application.

## UI-005 page dialogs and authentication

The Qt WebEngine `javaScriptDialogRequested` and
`authenticationDialogRequested` signals are handled in
`crates/browser-engine-qt/qml/Main.qml` for primary tabs, secondary windows,
and gesture-approved popups. They share a browser-owned modal surface that
shows a bounded, control-character-sanitized message, requesting host, and
appropriate alert/confirm/prompt/beforeunload or HTTP/proxy credential fields.
Page content cannot supply the surface's layout or iconography. Escape and
cancel/reject controls reject the request; beforeunload presents explicit
Stay/Leave choices; accepted prompt and credential values are bounded and are
not persisted.

Each live view resets its dialog budget at navigation start. A document may
open at most three dialogs, and the surface can suppress subsequent dialogs
for that document. Replacing a document, closing a tab/window, or destroying
a popup rejects its pending request before the view is released.

Build/runtime evidence:

```text
cargo xtask check
QT_QPA_PLATFORM=wayland timeout 10s target/debug/rustbrowser --temp-basedir
```

The build completed successfully and the native smoke remained alive until
the intentional timeout without QML load errors. Direct interaction with a

credential-server acceptance still need dedicated end-to-end coverage.
