# F02b1 — Diagnose and qualify secondary-host keyboard routing

**Parent:** F02b aggregate · **Lane:** presentation · **Type:** implementation · **Requirement:** EF-F02
**Dependencies (accepted, not just coded):** F02a
**Exclusive locks:** page-factory, primary-shell, secondary-shell, test-registration
**Acceptance:** T013 only · **Contracts:** C01, C02

## Outcome

Qualify the existing secondary-host keyboard parity behavior and distinguish native input routing from renderer delivery. Preserve the complete T013 assertion set.

## Work order

1. Reproduce T013 against accepted F02a source and retain its URL, title, history, settings, focus and page-key checks.
2. Before interpreting page delivery, assert the effective route for the injected key and observe a native KeyPress on the intended host. Focus or an attempted injection alone does not establish key delivery.
3. If native delivery is confirmed but the page misses the key, trace the production route and fix only a demonstrated defect in the allowlisted files. The current secondary key router lives in `FerricBrowserWindow.qml`; edit it only if the failure demonstrates that path is responsible.
4. Keep the case registered and non-skipping. If the runner cannot establish the route, native press or renderer cause, preserve the failing/blocked result and report the missing observation.

## Scope

Permitted files are the existing T013 test, current page/factory/primary-shell sources, and `FerricBrowserWindow.qml` for a reproduced router defect. Do not change acceptance expectations, omit the page-key assertion, or modify any unlisted path. The `test-registration` lock remains held for the shared harness.

## Verification and handoff

Run the exact registered `everyday_T013_factory_equivalence` gate with zero skips, plus required discovery and affected regressions, after the coordinator grants the native build lease. Record exact source and environment. Submit the result for independent review; F02b2 waits for acceptance.
