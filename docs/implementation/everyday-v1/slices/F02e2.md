# F02e2 — Implement Widgets host with embedded QML chrome

**Parent:** F02e · **Requirement:** EF-F02 · **Amendments:** A37, A42, A43, A44, A45, A46, A47, A48, A50

**Dependencies:** F02e1

## Outcome and steps

1. Keep the existing QApplication and add WebEngineWidgets/QuickWidgets to the pinned SDK module graph. Embed reusable existing QML chrome in a Widgets host; preserve appearance, geometry and native dialog parent identity.
2. Attach/detach the same owned QWebEnginePage for tab/window presentation. Host transfer preserves document state and never recreates a URL or admits a foreign profile.
3. Expose typed BrowserUi attach/detach operations through the existing bridge, keyed by opaque native-host/page-owner tokens and the existing TabId plus page/document generation. Validate the current live owner, profile context and generations in Rust, then reuse the existing `EngineEffect::ReparentView` through the native request lane. Extend that existing projection to carry captured page/document identity and host/page-owner tokens so stale requests are discarded before C++ resolves them and performs QWebEngineView attachment/lifetime work. Handle ReparentView explicitly in the existing typed input/request queue without changing order or dropping it. Reject stale, retired and foreign-profile requests without effects. Do not introduce a new core event/effect or parallel string command channel; if `ReparentView` cannot safely represent the operation, stop for another reviewed scope correction. Keep lifecycle policy outside QML; exercise focus, scale and safe host replacement.
